# 代码审查深度反思 — PR #57

## 1. 审查质量评估

### 覆盖度：增量本身审查偏薄，历史问题过度消耗配额

本次增量涉及 5 个文件，审查者对命令前缀重构的逻辑验证（命令树嵌套、权限节点、帮助文本）和 RulesLoader 重构的评价都是准确的。但存在两个覆盖盲区：

- **命令前缀兼容性风险未提及**：将 `fireflyauth`、`spawnall`、`playtime` 等独立前缀统一为 `fireflymc <sub>`，意味着玩家已有的命令别名/宏全部失效。如果存在外部文档、Wiki、或其他 mod 依赖这些前缀，这是破坏性变更。审查者未提出任何兼容性过渡方案（如保留旧前缀作为 deprecated alias）。
- **RulesLoader null 返回值的调用链未追踪**：审查者指出 `loadRules()` 失败返回 `null`，但未验证调用方 `RulesScreen` 是否完整处理了 null 路径。虽然变更中提到了"空公告占位提示"，但这是正面推断而非逆向验证——如果存在其他调用方呢？quick 模式下应至少 `grep` 一下 `loadRules` 的所有调用点。

### 准确度：严重程度标注合理，但决策与标注矛盾

3 个 major 的标注完全正确：反射空 catch 导致调试黑洞、恶意服务端注入负值 lockoutMinutes、跨线程可见性缺失。这些都是项目记忆中明确定义的规则（"网络请求禁止静默丢弃"、"网络包客户端防御校验"、"静态可变状态生命周期"）。

**但决策是 `comment` 而非 `request changes`**——这意味着 PR 可以在不修复这些 major 的情况下被合并。这与 major 的严重程度定义矛盾。如果问题真的够格 major，就应该 block；如果不 block，就说明实际上不认为是 major。这种"标注严厉但行动宽松"的模式会训练开发者忽略 major 标签。

### 完整性：对变更意图理解到位，对变更影响理解不足

审查者正确识别了两类改动（命令前缀统一 + RulesLoader 重构），但对第二类改动的**影响半径**评估不足。RulesLoader 从自定义文本解析切换为 JSON API 解析，这意味着：
- 解析数据源从本地/服务端内嵌文本变为外部 HTTP 依赖
- 网络延迟会直接影响规则加载时机
- 如果 API 不可用，用户体验从"显示旧规则"变为"显示空占位"

这些架构层面的影响变化在 quick 模式下被忽略了。

## 2. 发现的模式

### 代码模式：网络防御性编程系统性缺失

项目在"客户端接收外部数据"这个场景上存在系统性缺陷模式：
- `ModNetwork.java`：反射调用不记录异常 → 无法调试
- `ClientPayloadHandler.java`：网络字段不校验范围 → 可被恶意注入
- `RulesLoader.java`：网络错误静默丢弃 → 故障不可见

这三个问题本质上是同一个模式的三种表现形式：**对外部输入（网络包、反射结果、HTTP 响应）缺乏防御性处理**。项目记忆中已有对应规则，但规则是分散的（"网络请求禁止静默丢弃"、"网络包客户端防御校验"），开发者可能没有将它们关联为同一个设计原则。

### 架构观察：ClientState 作为全局状态中心的脆弱性

`ClientState` 被标记为红色高频问题模块，其核心问题是承担了过多的跨线程共享状态职责。`currentServerIp` 缺少 volatile 只是表象，根本原因是这个类的设计模式（大量静态可变字段 + 多线程读写）本身就容易出错。每次新增一个字段，开发者都需要记住加 volatile + reset() + closeHandler 调用，这种依赖"记住"的规范注定会失败。

## 3. 规范完善建议

### 新增规则：破坏性命令重构必须提供迁移路径

```
| 命令前缀/注册名变更 | 破坏玩家已有命令记忆和外部文档，必须提供 deprecated alias 或迁移公告 |
```

这条规则在当前规范速查表中完全缺失。Mixin 有兼容性验证要求，但命令注册名变更没有。

### 修改规则：major 标注与决策必须一致

当前规范定义了哪些问题算 major，但没有定义"标注 major 时必须 request changes"。建议补充：

```
| major 强制阻断 | 标注 major 的问题，决策不得为 comment/approve，必须为 request changes |
```

这可以解决"标注严厉但行动宽松"的矛盾，也能倒逼审查者谨慎使用 major 标签——如果不想 block，就降级为 suggestion。

### 新增规则：数据源切换必须评估可用性降级

```
| 数据源切换 | 从本地/内嵌数据源切换为网络数据源时，必须评估：离线降级方案、加载超时处理、用户体验变化 |
```

### 强化规则：同类缺陷批量修复应升级为阻断

项目记忆中已有"同类缺陷批量修复"规则，但 ModNetwork.java 的 5 处空 catch 已经 3+ 轮未修复。建议增加阈值机制：

```
| 同类缺陷修复阈值 | 同一文件同一模式缺陷超过 2 轮未修复，后续轮次直接 request changes，不再 comment |
```

## 4. 经验教训

### "顺带修复"的建议模式效果有限

审查者建议"RulesLoader 在本 PR 中被大幅重构，建议顺带补齐错误日志"。但开发者正在做的是命令前缀重构，RulesLoader 只是"顺手"改的。在这种心智模型下，"顺带再修一下日志"很容易被忽略，因为这不是当前任务的主线。

**更好的做法**：不要用"顺带"的语气。如果认为必须修，就单独标记为 issue 并明确 block；如果不 block，就接受当前状态，不在 comment 中制造模糊的义务感。

### quick 模式下历史问题的边际收益递减

ModNetwork.java 的空 catch 问题在项目记忆中已记录为"三轮修复失败，需资深开发者介入"。在第 4+ 轮继续标记相同问题，对代码质量的边际收益接近零，但对审查信噪比有显著负面影响——开发者会习惯性跳过这些"老面孔"评论，可能连带着忽略真正的新问题。

**建议**：对已确认 3 轮未修复的问题，停止在每次审查中重复标记，改为在 PR 级别做一次性的"遗留问题阻断声明"，直到看到实质性修复行动后再恢复逐项检查。

### 命令重构的测试验证缺失

审查者验证了命令树嵌套结构和权限节点，但没有验证实际运行时行为。对于命令注册变更，最可靠的验证方式是列出变更前后的命令注册表对比，确认：
- 新命令全部注册成功
- 旧命令全部注销（或保留为 alias）
- 无重复注册冲突

这在 quick 模式下可以通过要求开发者提供 `"/help fireflymc"` 的运行截图来低成本验证。

## 5. 增量审查反思

### 新增提交未解决之前问题，但也不应该解决

本次提交的意图是"重构命令前缀为 fireflymc"，3 个历史 major 问题分别位于 `ModNetwork.java`、`ClientPayloadHandler.java`、`ClientState.java`—— none of them 在本次变更范围内。要求开发者在做命令前缀重构时"顺手"修这三个不相关文件的问题，本身就不合理。

**反思**：增量审查中标记非增量范围内的历史问题，如果只是为了"提醒"，那应该用更轻量的方式（如引用已有 issue 链接），而不是每次都写完整的 major 评论。这会稀释审查的针对性。

### 增量变更本身未引入新风险

命令前缀重构是纯机械性的替换，风险可控。RulesLoader 重构虽然涉及数据源切换，但代码质量确实提升（-87/+35，解析逻辑更健壮）。本次增量本身的安全性是好的。

### 覆盖度确实因 quick 模式而下降

最明显的体现：RulesLoader 从本地解析切换为 HTTP API 解析，但审查者没有检查：
- HttpClient 实例是否复用（规范明确要求"禁止方法内重复创建"）
- 请求是否有超时设置（规范要求"P2P 超时强制兜底"的同类精神）
- 是否有重试机制的退避策略

这些在 quick 模式下被跳过了，但在全量审查中按"配置→触发→传输→处理→展示→清理"链路扫描时应该能覆盖到。

### 总结：6/10 评分的合理性

如果只看增量变更质量，本次应该拿到 8/10（命令重构正确、RulesLoader 精简有效）。6/10 的评分几乎完全被历史问题拉低。这种评分方式在增量审查中会造成误导——开发者会认为"我这次改得不好"，但实际上是"历史债务没有偿还"。建议增量审查将"增量质量分"和"债务偿还分"分开展示，让开发者清晰知道当前变更本身的水准。
