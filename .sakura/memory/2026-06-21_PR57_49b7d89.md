# 全量重审深度反思 — PR #57

## 1. 审查质量评估

### 覆盖度：存在明确盲区

按链路组织审查是正确的策略，但导致**非核心链路的变更文件被系统性遗漏**：

| 遗漏文件 | 改动量 | 风险评估 |
|----------|--------|----------|
| `PasswordAuthScreen` | **+19** | 🔴 与登录锁定直接相关的 UI，完全未提及 |
| `ClientEventNotificationMessage` | +10 | 🟡 事件通知链路的数据结构变更，未说明 |
| `ModEventHandler` | +2/-2 | 🟢 改动极小，可接受 |
| `ClientEventWebSocketClient` | +1 | 🟢 改动极小，可接受 |

**最严重的遗漏是 `PasswordAuthScreen`**。登录锁定机制的链路审查中，"UI 拦截"环节只审查了 `ConnectScreenMixin`，但 `PasswordAuthScreen` 作为密码输入界面，+19 行变更可能涉及锁定状态下的 UI 禁用/提示逻辑，直接关系到用户体验和防绕过，却完全不在审查范围内。

### 准确度：标记合理，但有一处值得商榷

- **ModNetwork 空 catch → major**：准确。项目记忆明确记录这是"三轮修复失败"的高频问题，且本次**新增代码延续缺陷模式**比历史缺陷本身更严重，反映了开发者对审查反馈的忽视。
- **lockoutMinutes 缺校验 → major**：准确。严格符合"网络包客户端防御校验"规范。
- **currentServerIp 缺 volatile → minor**：**偏轻**。该字段作为 `ClientAuthLockoutManager` 的 key 来源，可见性问题可能导致锁定记录写入错误 key，间接削弱锁定机制有效性。结合 `ClientState` 是 🔴 高频问题模块的历史，建议提升为 major 或至少在评论中明确论证降级理由。

### 完整性：链路理解到位，但点状遗漏

对登录锁定机制的端到端链路理解准确——特别是"先下发 Payload 再 disconnect 的包序正确性"和"用 currentServerIp 拼 key 避免 disconnect 时序竞争"这两个细节，说明审查者确实深入读了代码时序。但对 `ConnectScreenMixin` 中提到的"修复原来关机拦截后仍执行后续检查的遗留问题"一笔带过，未追问：这个 bug 引入于哪个版本？影响范围？是否需要补 changelog？

## 2. 发现的模式

### 代码模式

1. **缺陷模式惯性**：ModNetwork 空 catch 已被标记三轮，开发者非但未修复历史实例，新增代码还延续该模式。这不是"忘了修"，而是**开发者认为空 catch 是可接受的模式**，需要从认知层面纠正。
2. **审查反馈吸收不均**：`ClientAuthLockoutManager` 正确使用了 synchronized 保护组合操作（吸收了"组合操作原子性"规范），但同 PR 中 `currentServerIp` 又漏了 volatile（未吸收"静态状态必须 volatile"规范）。说明开发者是**按点修复**而非**内化规则**。
3. **版本号硬编码已收敛**：`FireflyMCMod.VERSION` 统一引用在 HUDRenderer/ModUpdateScreen 中落实，说明之前的规范提示有效。

### 架构观察

`ModNetwork` 的反射分发机制是空 catch 的**结构性根源**。每次新增 Payload 都要手写反射调用 + try-catch，这是"设计迫使犯错"。不重构分发机制，空 catch 问题会无限再生。

## 3. 规范完善建议

### 新增规则

| 规则 | 说明 | 触发条件 |
|------|------|----------|
| **缺陷模式延续升级** | 已标记的模式缺陷（如空 catch），若同文件新增代码延续该模式，严重等级自动提升一级 | 历史评论中存在同模式缺陷 |
| **全量审查文件覆盖率硬约束** | 审查摘要必须包含所有变更文件的审查结论，至少一行；>10 行变更的文件必须有实质性审查内容 | `/full-review` 模式 |
| **遗留 bug 修复须追溯** | 审查中发现的"修复遗留问题"须注明：引入版本、影响范围、是否需 changelog | 评论中提及"遗留/修复"关键词 |

### 修改规则

- **"网络包客户端防御校验"补充量化标准**：当前只说"须做范围校验"，建议明确"数值字段校验缺失默认 major，与安全机制关联的升级为 blocking"
- **"同类缺陷批量修复"增加执行力**：当前规则是"须列出所有实例一并修复"，但 ModNetwork 三轮未修复说明规则缺乏约束力。建议改为"同类模式缺陷 >3 处且跨 >2 轮未修复，标记为 blocking 并建议重构"

## 4. 经验教训

### 值得关注的要点

1. **区分"不会修"和"不认同"**：ModNetwork 空 catch 三轮未修复，可能不是能力问题而是开发者不认为这是问题。后续评论应增加**后果论证**（如："空 catch 导致反射失败时客户端无任何日志，线上问题完全无法排查"），而非仅说"禁止空 catch"。
2. **`PasswordAuthScreen` 类文件的审查策略**：UI 文件经常在链路审查中被遗漏，因为它既不属于"网络传输"也不属于"业务逻辑"。建议在链路组织中增加"交互展示"显式环节。
3. **BindCommandHandler 的 suggestion 过于温和**：未检查 WebSocket 连接状态就打开浏览器，如果 WebSocket 断开，用户打开绑定页面后超时无响应，这是**功能失效**而非"建议改进"。应至少标记 minor。

### 技术经验

- **ConnectScreenMixin 的 return 修复**揭示了一类常见 Mixin 陷阱：多个 `@Inject` 在同一注入点时，前一个拦截后的 `return` 行为需要显式处理，否则后续注入仍会执行。这应补充到 Mixin 审查要点中。

## 5. 手动全量重审专项反思

### 全量 vs 增量的增量价值

本次全量重审相比假设的增量审查，主要增量价值在于：
- ✅ 发现了 ModNetwork 新增代码延续空 catch 模式（增量可能只看新代码，不会关联历史模式）
- ✅ 发现了 `currentServerIp` 缺 volatile（增量可能不扫 ClientState 全文）
- ✅ 链路视角下验证了包序正确性和时序安全性

### 全量审查本身的遗漏

但全量审查**并未达到"全量"承诺**——18 个变更文件中至少 2 个有实质改动（>10 行）的文件完全未覆盖。原因分析：

**根因：链路组织方式的固有盲区**。按功能链路组织时，审查者的注意力沿链路流转，容易忽略"属于某条链路但文件名不直观"的文件（`PasswordAuthScreen` vs `ConnectScreenMixin`，前者不像"拦截"文件）。

**改进方案**：全量审查采用**两阶段**——第一阶段按链路组织（保证深度），第二阶段用变更文件列表做 **checklist 式兜底**（保证广度），对第一阶段未提及的文件强制补充审查结论。
