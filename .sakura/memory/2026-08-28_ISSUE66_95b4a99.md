**6️⃣ 经验教训 & 后续关注要点**  
| 经验点 | 说明 |
|--------|------|
| **需求边界明确** | Issue 中混合了 “AI 配置勾选” 与 “Issue 分析查看图片” 两个层面，分析时要先拆解需求，区分 *仓库可实现* 与 *外部服务* 的职责，防止误导。 |
| **多模态改动的传播链** | 多模态涉及 **序列化 → 配置 → 历史管理 → 网络请求 → 日志脱敏**，每一步都要检查项目的通用审查要点（日志脱敏、异常记录、配置热更新）。建议在改动前绘制 **功能链路图**，确保不遗漏任何环节。 |
| **兼容性与迁移** | 改动 `ApiMessage` 的结构会影响已有持久化或缓存（如 `.sakura/memory`），需提供 **向后兼容**（如旧字段保留、默认值）或 **迁移脚本**。 |
| **隐私默认安全** | 涉及用户图片时，必须在配置层面默认 `false`，并在日志、异常中脱敏；这与仓库的 “隐私外传配置默认 false” 规则高度吻合，后续类似需求应直接引用该规则。 |
| **单元测试必不可少** | 结构变更后，所有 **API 调用**、**序列化**、**历史裁剪** 必须补充单元测试；尤其是多模态数组的 `content` 序列化/反序列化，需要覆盖 **空图片、异常 URL、超大图片** 场景。 |
| **文档同步** | 新增配置项后，需要在 `zh_cn.json`、`en_us.json`、`README`、以及插件的配置说明中同步更新，否则使用者难以发现。 |
| **重复检测加强** | 对于功能类 Issue，建议在检测时使用 **语义相似度**（如向量匹配）而非仅关键词，以降低漏报概率。 |
| **标签体系维护** | 项目应维护一个 **标签清单**（含置信度阈值），自动建议标签时参考该清单，避免出现低置信度的 `help wanted` 等不常用标签。 |
