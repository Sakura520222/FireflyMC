**二、发现的模式**

| 模式 | 具体表现 | 影响 |
|------|----------|------|
| **fail‑closed 设计** | `ensureInitialized` 所有异常路径统一返回 `false`，并让调用方 (`MusicPlayer`) 完全关闭读写。 | 提高了系统在不可靠磁盘环境下的容错性，契约明确。 |
| **幂等初始化** | `ensureInitialized` 在成功后 `initialized` 标记不再重置，后续调用直接返回 `true`，避免重复迁移。 | 对资源竞争友好，但需确保 `initialized` 的可见性（已确认单线程使用）。 |
| **资源清理统一** | `cancel()` 与 `finally` 中统一调用 `deletePartFile(null)`，并在 `deletePartFile` 内部对 `null` 做容错。 | 防止残留临时文件泄漏。 |
| **测试同步更新滞后** | 代码路径新增（fail‑closed），但对应的负面路径测试仍缺失。 | 容易在后续改动中产生回归。 |
| **日志计数误导** | `wipeLegacyCache` 计数包括删除失败的文件，导致 “已删 N 个” 与实际成功数不符。 | 在故障排查时容易误判清理成功率。 |
| **异常路径未统一日志** | 本次改动中对 `writeFormatMarker` 失败仅记录 `warn`，未使用统一的脱敏日志方法。 | 与项目 **日志脱敏全级别覆盖** 规则不完全匹配。 |

**三、规范完善建议**

1. **新增/强化审查规则**  
   - **Rule‑TC‑FAILCLOSED**：所有对外提供的“禁用/启用”契约方法（如 `ensureInitialized`）必须配套 **至少一个** 失败路径的单元测试，且测试应验证状态保持不变、标记文件不生成。  
   - **Rule‑LOG‑COUNT‑CONSISTENCY**：对任何统计/计数日志（如 “已删 X 个文件”），计数必须仅基于 **成功** 操作的返回值，避免误导。审查时检查 `forEach`/`stream` 中是否有 `try/catch` 后仍计数的情况。  
   - **Rule‑LOG‑SANITIZE‑ALL**：同一方法内所有日志级别必须统一使用项目提供的脱敏函数 `logSafe()`，审查时对新增日志点进行检查。  
   - **Rule‑TEST‑EXCEPTION‑PATH**：对每条 `catch`、`if (!condition) return false` 等异常/错误路径，要求至少 **一个** 对应的单元测试（可使用可移植的文件系统异常注入）。  

2. **项目特有的规范要点**  
   - **缓存契约文档同步**：`MusicCache` 的 Javadoc 中声明的 “禁读防旧坏缓存、禁写防合法 v2 被下次迁移误删” 必须在代码实现的每个分支里显式注释对应的契约点，防止以后改动时契约被破坏。  
   - **幂等性检测**：对所有 `ensure*`、`initialize*` 类方法，审查应验证 **幂等**（重复调用不产生副作用）并在测试中加入幂等性验证。  
   - **计数/统计 API 返回值**：如 `deleteQuietly` 建议改为返回 `boolean`，并在所有调用处只在成功时计数，保持统计语义一致。  

**四、经验教训**

| 教训 | 具体表现 | 今后关注点 |
|------|----------|-----------|
| **测试覆盖不完整会导致契约失效** | `ensureInitialized` 的 `false` 路径缺失测试，审查只能凭代码阅读判断安全性。 | 在审查时主动检查 **异常路径测试**，若缺失立即提出补全。 |
| **计数日志的语义要与实现匹配** | `wipeLegacyCache` 计数包括失败删除，导致日志误导。 | 对所有 **统计/计数** 类日志，审查其计数依据是否与实际成功操作对应。 |
| **日志脱敏规则容易被忽视** | 本次新增的 `warn` 日志未使用统一脱敏方法。 | 在审查每个新日志点时，检查是否走统一的脱敏入口。 |
| **增量审查易产生视野盲点** | 只关注新增的 `ensureInitialized` 失败路径，却未检查旧代码中可能的 **异常路径未记录日志**（如 `writeFormatMarker`）。 | 增量审查时，应把 **“受影响的公共契约/接口”** 作为审查范围，回顾该接口的全部实现与调用链。 |
| **代码改动与文档同步** | Javadoc 中的缓存禁用契约与实现保持一致，但如果以后有人修改实现而忘记更新注释，契约会失效。 | 强化 **代码‑文档一致性** 检查，尤其是对关键契约的 Javadoc。 |

**五、增量审查反思**

| 维度 | 观察 | 结论 |
|------|------|------|
| **是否解决了前轮审查的问题** | - 迁移失败导致的旧缓存仍被读取的问题已彻底闭环（`cacheReady` 统一判断）。<br>- 全新安装时的目录缺失误判已通过 `createDirectories` 前置解决。 | ✅ 完全解决了前轮提出的核心缺陷。 |
| **是否引入了新风险** | - `wipeLegacyCache` 计数误导（已在审查中指出）。<br>- `ensureInitialized` 失败路径缺少单元测试，仍是潜在回归点。<br>- 新增日志未走统一脱敏路径。 | ⚠️ 新风险主要在可观测性和测试覆盖上，功能层面未出现新缺陷。 |
| **审查覆盖度的变化** | 增量审查聚焦于 **缓存禁用契约** 与 **目录创建顺序**，导致对 **日志统一性**、**计数语义** 等横向影响点的发现相对较少。 | 需要在增量审查中加入 **“横向影响检查”**（如日志、计数、异常路径）以避免视野收窄。 |

---

### 综合建议

1. **在增量审查流程中加入横向检查清单**：除关注直接改动外，列出 “日志、统计、异常路径、公共契约” 等横向因素，一并审查。  
2. **强制异常路径单元测试**：将 **Rule‑TC‑FAILCLOSED** 纳入项目 CI 检查，缺失时 CI 直接报错。  
3. **统一计数/日志实现**：把 `deleteQuietly` 改为返回 `boolean`，并在 `wipeLegacyCache`、`invalidate`、`cleanStaleParts` 等处统一使用返回值计数。  
4. **日志脱敏审查自动化**：在代码审查工具中加入对 `log*` 调用的正则匹配，提示是否使用 `logSafe()`。  

通过上述改进，可在保持高效增量审查的同时，进一步提升代码的安全可靠性与可维护性。
