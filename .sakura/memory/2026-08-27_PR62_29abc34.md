### 2.2 项目架构观察  
1. **功能链路清晰**：点歌功能从 **配置 → 请求 → 搜索 → 缓存 → 播放 → 队列管理 → UI/指令**，每一步都有对应的类/常量。  
2. **依赖集中**：第三方 MP3 解码依赖 JLayer，仅在 `build.gradle` 中通过 `jarJar` 引入，避免冲突。  
3. **配置文件分离**：`fireflymc-client.toml` 与 `fireflymc-server.toml` 明确划分，然而文档在说明 `music_settings.requestVolume` 时未标明其归属，导致潜在使用者误查。  
4. **指令输出量潜在风险**：`queue` 指令一次性遍历完整队列（最多 50 条），直接写入聊天栏，可能导致刷屏。实现层面暂无分页或截断逻辑。

## 3. 规范完善建议  

### 3.1 针对本次审查的规则补充  

| 新增/修改规则 | 目的 | 适用范围 |
|---------------|------|----------|
| **文档‑代码一致性检查** | 自动抽取 `Config.java`、指令注册、常量定义等关键信息，对比 README 中的描述，确保每个配置项、指令、常量的说明与实现保持同步。 | 所有文档改动（README、wiki、CHANGELOG） |
| **配置归属标注** | 当文档中出现配置项时，必须在同一行或紧邻位置标注该配置所在的 **toml** 文件（client / server），避免使用者在错误文件中搜索。 | `README.md`、`docs/` 中的配置章节 |
| **长输出警示** | 对任何可能一次性输出 >30 行的指令（如 `queue`），文档必须注明 “可能刷屏”。若实现中未提供分页/截断，则建议在代码层面添加 `maxPrintLines` 限制。 | 指令实现类（`MusicCommandHandler`）及对应文档 |
| **许可证合规细化** | 除了列出 LICENSE、NOTICE、gradle 配置外，还需检查 **源码分发**、**二进制分发方式** 是否满足 LGPL‑2.1（例如提供源码压缩包或链接）。 | `build.gradle`、`LICENSES/`、`NOTICE.md` |
| **文档变更 CI 检查** | 在 CI 中加入 `markdown-link-check`、`spell-check`、以及自定义脚本比对关键字（如 `MusicQueueManager.PLAYER_SONG_LIMIT`）是否出现于文档。 | PR CI 流程 |

### 3.2 项目特有的规范要点  

1. **配置热更新可见性**：若配置支持热更新（如 `requestVolume`），文档必须说明 “修改后即时生效”。  
2. **指令权限标记**：每条指令的文档必须标注是否需要 OP 权限或特权等级。  
3. **缓存容量阈值**：文档中出现缓存大小时，必须给出单位（MB）并说明 “超过此容量时会自动淘汰最早使用的条目”。  
4. **依赖许可证统一目录**：所有第三方库的许可证文件必须放在 `licenses/`，并在 `NOTICE.md` 中提供清单，CI 检查目录完整性。
