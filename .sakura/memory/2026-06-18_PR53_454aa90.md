# 全量重审深度反思 — PR #53 (v2.5.4)

## 1. 审查质量评估

### 覆盖度：有显著盲区

**做得好的部分：**
- 精准命中 3 个分散在不同文件中的 `volatile` 缺失，这类跨文件同类缺陷在增量审查中极易漏掉，全量审查的价值在此体现
- IPv6 ULA 泄漏问题展现了深度的 API 层面理解（知道 `isSiteLocalAddress()` 不覆盖 `fd00::/8`），不是浮于表面的审查
- 隐私默认值问题从代码审查延伸到了产品层面，值得肯定

**遗漏的部分：**
- **ConnectScreenMixin（+47行）**：项目记忆明确要求新增 Mixin 必须评估 mapping 兼容性与模组冲突，但本次审查**完全未提及**，这是规则存在但未执行的典型案例
- **ClientEventNotificationEvents（+71行）**：触发"新增文件 >50 行必须有审查意见"规则，但摘要中无任何意见，说明审查时未按规则逐项 checklist 核验
- **ServerShutdownManager（+71行）**：只追踪到了它对 `ClientState.serverShutdown` 的写入，但未审查其自身的状态生命周期——关机状态在连接断开/重连时是否正确重置？`closeHandler` 链是否覆盖？
- **RelayGuestJoiner（+100/-10）**：最大改动文件，除 `activeP2PProxy` 外，`join()` 方法中"状态赋值 + 网络操作"的组合操作原子性未被审视
- **断线重连机制**：新增的 `ClientEventNotificationConfig` 相关 WebSocket 链路是否具备重连能力？项目记忆明确标注为"阻塞级缺陷"，但未看到审查结论

### 准确度：无误判

4 个 `major` 严重程度合理——跨线程无 `volatile` 在 Minecraft mod 中确实会导致可见性问题，不是理论风险而是实际会触发的。IPv6 ULA 泄漏直接导致功能失效，`major` 恰当。`minor` 和 `suggestion` 分级也准确。

### 完整性：功能理解到位，但规则执行不到位

三项新功能（IPv6 P2P、伪关机、跨级聊天）均被识别并审查了核心逻辑。但对每个功能周边的"基建性"要求（Mixin 兼容性、重连机制、状态重置）覆盖不足。

## 2. 发现的模式

### 代码模式
- **静态可变状态泛滥**：第 21 次反思，`volatile` 缺失仍是最高频问题。项目习惯用静态字段做跨组件通信，但线程安全意识未同步跟上
- **忙轮询惯性**：`while+sleep` 已被标记为"项目已知反模式"，但新增代码仍在沿用，说明缺乏统一的并发工具类来替代
- **回调线程 → 主线程的单向数据流**：WebSocket 回调写状态、主线程读状态是固定模式，但每次新增都漏 `volatile`

### 架构观察
- 本次 PR 体现了"功能驱动"而非"基建驱动"的开发风格——新功能快速落地，但线程安全、状态生命周期等横切关注点总是后补
- `RelayGuestJoiner` 承担了过多职责（P2P 代理创建、中转逻辑、静态状态管理），是竞态条件的高发区

## 3. 规范完善建议

### 新增规则

| 规则 | 说明 |
|------|------|
| **新增文件审查清单强制化** | 审查流程必须先生成"新增文件列表"，逐文件核对：>50行是否有意见、Mixin是否有兼容性评估、是否有状态生命周期 |
| **隐私外传配置默认值** | 涉及用户数据上传的配置项，默认值必须为 `false`，违反即标记 `major` |
| **WebSocket 链路审查三件套** | 新增/修改 WebSocket 相关代码必须显式回答：(1)重连机制 (2)回调线程安全 (3)closeHandler 覆盖，缺失任一标记 `major` |

### 修改规则

| 现有规则 | 修改建议 |
|----------|----------|
| 静态可变状态必须 volatile/AtomicBoolean | 升级为：**静态可变状态缺失并发修饰，无例外标记 `major`**，不再容忍"目前都在主线程"的 `minor` 降级 |
| 新增 Mixin 必须评估兼容性 | 改为：**审查输出必须包含 Mixin 兼容性评估段落，缺失视为审查不完整** |
| 忙轮询必须标记 suggestion | 升级为：**新增代码中出现 while+sleep 直接标记 `minor`**，已知反模式不应再以 suggestion 级别放过 |

## 4. 经验教训

1. **全量审查需要 checklist 驱动，不能靠记忆**：本次遗漏的 Mixin 兼容性、新增文件审查规则，全部在项目记忆中有明文规定。问题不是规则不够，而是审查时没有逐条勾选。建议审查模板内置 checklist。

2. **"追踪写入源"的审查策略有效但不够**：通过 `ServerShutdownManager.onShutdownStateChanged()` 追踪到 `ClientState.serverShutdown` 的写入源，这个方法很好。但应该同时追问：**这个写入源的完整生命周期是什么？谁重置它？**

3. **大改动文件需要独立深度审查**：`RelayGuestJoiner` 净增 90 行、`P2PConnectionManager` 净增 63 行、`ReliableUdpChannel` 净增 108 行，这些文件不应只看被举报的具体字段，而应对整个方法做控制流分析。

4. **IPv6 知识沉淀**：`isSiteLocalAddress()` 不覆盖 ULA 这个坑值得写入项目编码指南，避免未来其他开发者重犯。

## 5. 手动全量重审反思

用户触发全量重审，推测原因可能是增量审查遗漏了跨文件的系统性问题。从结果看：

- **全量审查确实发现了增量模式容易漏的问题**：3 个 `volatile` 缺失分散在 `ClientState`、`P2PGuestProxy`、`RelayGuestJoiner` 三个文件中，增量审查如果按文件拆分极易漏掉整体模式
- **但全量审查的"广度陷阱"也暴露了**：审查精力被分散到 20 个文件后，反而漏掉了对单个新增文件的规则化检查（Mixin、>50行文件）。这说明全量审查不能只是"把范围扩大"，而需要**结构化**——先按规则维度扫全量，再按文件维度深入

**改进建议**：未来全量审查分两轮——第一轮"规则驱动"（按 checklist 逐条在全量代码中搜索匹配），第二轮"文件驱动"（对每个新增/大改文件做独立深度审查）。本次 essentially 只做了第二轮且做得不够彻底。
