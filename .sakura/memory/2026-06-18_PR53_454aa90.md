## 2. 发现的模式

### 代码模式

```java
// 模式1: 链式清理回调
channel.setCloseHandler(() -> {
    proxy.cleanup();
    joiner.reset();  // 但这条链可能断裂
});

// 模式2: 忙轮询背压（待优化）
while (sendWindow.isFull()) {
    Thread.sleep(5);  // 应改为 Condition.await()
}

// 模式3: 静态状态作为跨组件通信
ClientState.serverShutdown = true;  // 缺少 volatile
```

### 架构观察

```
云端指令 ──→ EventWS ──→ ServerShutdownManager
                              ↓
                      ConnectScreenMixin (拦截UI)
                              ↓
                      显示"维护中"界面

P2P 打洞流程：
LobbyWS ──→ candidate交换 ──→ P2PConnectionManager
                                    ↓
                            Ipv6AddressCollector (新增)
                                    ↓
                            双栈UDP Socket创建
                                    ↓
                            ReliableUdpChannel ──→ SendWindow
```

架构清晰，但**静态状态作为组件间通信媒介**的模式在扩展时会带来维护负担。

## 3. 规范完善建议

### 新增规则

| 规则 | 说明 | 触发条件 |
|------|------|----------|
| **新增文件强制问题发现** | 新增 `.java` 文件必须有至少 1 条审查意见（可为 positive） | 文件新增行数 > 50 |
| **忙轮询检测** | `Thread.sleep` 在循环中使用必须标记 suggestion | 检测到 `while.*sleep` 模式 |
| **IPv6 地址过滤审查** | IPv6 收集器必须验证不上报 link-local/ULA 地址 | 涉及 `Inet6Address` 收集 |
| **Mixin 冲突风险评估** | 新增 Mixin 类必须说明注入点与其他模组的兼容性 | 新增 `*Mixin.java` |
| **closeHandler 链完整性** | 资源清理链必须覆盖所有异常断开路径 | 涉及 `setCloseHandler` |

### 修改现有规则

**静态状态必须可重置** → 细化为：
> 静态可变状态必须：(1) `volatile` 修饰；(2) 提供 `reset()` 方法；(3) 在 closeHandler 链末端调用 reset

## 4. 经验教训

### 4.1 大版本更新的审查策略失误

v2.5.4 新增 829 行代码，涉及 4 个独立特性。全量审查时容易：
- 被 IPv6 的新鲜感吸引，忽视成熟的 P2P 模块中的细微问题
- 对新增文件产生"新代码应该没问题"的潜意识偏见

**对策**：大版本更新应按特性拆分审查清单，逐项打勾。

### 4.2 网络模块的"正常路径"偏好

审查自然聚焦于数据发送/接收的主路径，但对以下边界路径覆盖不足：
- IPv6 收集失败时的降级日志
- 伪关机指令到达时玩家正在加载的竞态
- FIN 握手半开状态的超时清理

### 4.3 背压机制的审查深度不够

`awaitWindowSpace` 被标记为 suggestion，但应评估：
- 5ms 轮询在高延迟网络下是否合理？
- 窗口满 5 秒后是丢弃还是阻塞？对 MC 主线程的影响？
- 与 Minecraft 的 tick 循环是否有交互？

## 5. 手动全量重审反思

### 全量 vs 增量的发现差异

假设之前存在增量审查，本次全量重审的价值：

| 维度 | 增量审查可能遗漏 | 全量审查是否补足 |
|------|------------------|------------------|
| 跨文件状态流 | ✅ `ClientState` 被多文件修改 | ✅ 发现 volatile 缺失 |
| 新增文件与旧代码的交互 | ❌ `Ipv6AddressCollector` 如何融入现有打洞流程 | ❌ 未审查 |
| 历史债务 | ❌ 旧代码中的潜在问题 | ⚠️ 部分覆盖 |

### 全量审查的局限

即使全量审查，仍然受限于：
1. **时间压力**：20 个文件 +829 行，单次审查难以深入每个文件
2. **认知负荷**：同时理解 IPv6、可靠 UDP、伪关机、跨级聊天四个特性容易疲劳
3. **缺乏运行时验证**：静态审查无法验证 Mixin 注入时序、UDP 打洞实际行为

### 改进建议

对于类似规模的全量审查：
1. **分特性审查**：将 PR 拆为 4 个虚拟子任务，分别审查
2. **新增文件专项**：对 3 个新增文件进行独立深度审查
3. **状态流追踪**：画出 `ClientState` 所有读写点，验证线程安全

## 总结

本次审查质量 **7.5/10**，主要问题是对新增文件和大幅修改文件的覆盖不足。8 分的评分可能偏高，考虑到：
- 3 个新增文件零问题发现
- `P2PConnectionManager` 84 行修改零问题
- 背压机制仅作 suggestion 而非评估实际影响

建议在项目记忆中增加"新增文件强制审查"和"忙轮询检测"规则，并在下次大版本更新时采用分特性审查策略。
