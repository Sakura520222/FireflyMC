### 2. 发现的模式

- **代码模式**：
  - **日志脱敏采用正则替换 JSON 字段值**：该方法直接有效，但存在过度匹配风险。这是快速实现数据安全的一种常用但粗糙的手段。

- **架构观察**：
  - **P2P 与 Relay 模块耦合较紧**： `RelayLobbyWebSocketClient` 负责发送包含 P2P 地址的中控消息，而脱敏逻辑被放置在此处而非更底层的日志框架或通用工具类。这可能意味着项目缺少统一的敏感数据过滤层。
  - **对字符串处理的性能敏感度低**：正则、字符串拼接在关键路径上被使用（即使注释称“GC压力极小”），说明项目优先保证功能正确性，暂未进入极致的性能优化阶段。

### 3. 规范完善建议

基于本次审查，建议新增或强调以下规则：

| 规则 | 说明 |
|------|------|
| **日志脱敏必须统一** | 新增任何日志输出，若可能包含用户 IP、token、P2P 地址等敏感信息，必须经过脱敏函数。建议封装 `logSafe()` 工具方法，强制所有模块使用。 |
| **同一数据源的日志处理策略一致** | 对同一个原始对象（如 `json` 字符串），无论日志级别（debug/info/warn），其脱敏行为必须一致，防止调试时通过切换日志级别意外泄露数据。 |
| **脱敏正则的范围审查** | 对于通配匹配（如 `"address"` 字段），需在 PR 描述中明确其可能误杀的场景，并评估风险。若无法精确匹配，应记录决策原因。 |

### 4. 经验教训

- **增量审查的天然局限**：本次审查完美发现增量中的小问题，但完全未提及历史存在的重大线程安全问题。项目积累的“项目记忆”中列出的大量待修复点（`webSocket` 字段访问、`executor` 阻塞、`textAccumulator` 未同步等）依然存在。**单一提交的增量审查不应被视为对模块整体质量的背书**。
- **敏感数据修复需全局排查**：当修复一类泄露问题（如 IP 地址）时，不能只改已有日志，还需检查所有新加入的日志语句（如本次 debug 分支）。审查时建议用 `grep` 辅助检查同文件中其他日志点。
- **字符串操作并非总是无害**：虽然本次 “`address + ":" + port`” 的 GC 影响极小，但在高频 P2P 连接管理中应保持警惕。这是一个好的意识提醒。
