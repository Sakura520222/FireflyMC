## 2. 发现的模式  

### 代码模式  

| 模式 | 说明 | 影响 |
|------|------|------|
| **重复的日志脱敏调用** | 多处手动 `sanitize()`，但并未统一封装为 `logSafe()`。 | 易产生遗漏（如本次的 `onClientFailure`），导致脱敏不一致。 |
| **硬编码阈值** | `EARLY_EOF_TOLERANCE_MS`、`FALLBACK_DURATION_MS`、重试次数/间隔等直接写在代码里。 | 难以在不同环境或运营配置中调优，且容易在需求变更时遗漏更新。 |
| **异常捕获后仅记录** | 部分 `catch (Throwable e)` 只 `log.warn`，未上报或做后续处理。 | 与项目记忆中的“异常日志统一记录”不完全匹配，潜在的错误隐蔽。 |
| **单线程 Executor 中使用 `join()`** | `MusicPlaybackManager` 中对 `CompletableFuture` 使用 `join()`，导致阻塞。 | 虽未导致本次死锁，但是潜在的阻塞风险。 |
| **HTTP 客户端配置散落** | `HttpSchemePolicy`、`Redirect` 配置分散在不同类，缺少统一入口。 | 容易产生不一致的安全策略（如本次明文依赖）。 |

### 架构观察  

1. **音乐子系统高度耦合**：`MusicPlayer`、`MusicCache`、`MusicPlaybackManager`、`MusicApiClient`、`MusicServerBridge` 之间相互调用频繁，状态管理通过共享对象（如 `songId`）进行。  
2. **网络层与业务层混杂**：`MusicServerBridge` 同时负责日志、错误上报、协议转换，导致日志脱敏、错误码映射等职责交叉。  
3. **配置/阈值缺乏统一入口**：所有阈值、重试次数、容差均硬编码在业务类中，缺少统一的 `MusicConfig` 或 `ModConfig`。  
4. **异常恢复路径分散**：流恢复、EOF 判定、重连策略在多个类里分别实现，缺少统一的 “恢复策略” 抽象层，导致策略不一致（如 EOF 与 fallback 的冲突）。  

## 3. 规范完善建议  

### 新增/修改审查规则  

| 规则 | 建议内容 |
|------|----------|
| **日志脱敏全级别覆盖** | 强制所有日志入口使用统一工具 `LogSanitizer.sanitize()`（或 `logSafe()`），审查时检查同文件/同类日志点是否一致。 |
| **阈值配置化** | 所有业务阈值（重试次数、间隔、EOF 容差、fallback 时长）必须通过 `ModConfig` 或构造函数注入，禁止硬编码。审查时搜索 `= <数字>` 并确认是否已抽取。 |
| **异常日志完整记录** | `catch (Throwable e)` 必须同时记录 `log.error(..., e)` 并上报到统一的错误上报系统（如 `ClientMusicFailReporter`），禁止仅 `log.warn`。 |
| **单线程 Executor 禁止阻塞** | 检查所有 `Executor` 或 `ForkJoinPool` 中的 `join()`、`get()` 调用，必须配合 `orTimeout` 或改为回调式处理。 |
| **HTTP 重定向安全** | 所有 `HttpClient` 必须设置 `Redirect.NEVER`，或在重定向后显式校验 `uri.getScheme()` 为 `https`，审查时检查 `Redirect` 枚举使用情况。 |
| **早 EOF 判定容差统一** | 为 `EARLY_EOF_TOLERANCE_MS`、`FALLBACK_DURATION_MS` 建立统一常量或配置，并在文档中说明其业务意义。 |
| **并发安全检查** | 对涉及共享缓存（`MusicCache`）或全局状态（`ModNetwork`）的读写，审查时确保使用 `synchronized`/`ReentrantLock`/`Concurrent*` 并检查是否有 `volatile`/`Atomic*` 修饰。 |
| **统一异常恢复策略** | 引入 `StreamRecoveryStrategy` 接口，所有流恢复路径必须实现统一的 `recover()` 方法，审查时检查是否直接在业务类中散落实现。 |

### 项目特有规范要点  

1. **Music 模块日志脱敏**：在 `firefly520/fireflymc/client/music/**` 下所有日志点必须使用 `MusicLogUtil.sanitize()`，并在 `MusicLogUtil` 中统一实现。  
2. **网络错误码映射**：`ClientMusicFailReporter` 必须在 `enum FailureCode` 变更时同步更新对应的网络错误码映射表，审查时检查 `switch`/`map` 是否完整。  
3. **音频资源释放**：`JavaSoundOutput.tryOpen()` 重试成功后必须在 `finally` 中确保 `Line` 正确关闭/释放，防止资源泄漏导致后续 `LineUnavailableException`。  

## 4. 经验教训  

| 教训 | 对策 |
|------|------|
| **脱敏遗漏容易被忽视** | 将脱敏工具加入 **IDE 检查**（如自定义 Checkstyle/SpotBugs 规则），在 PR 检查清单中强制列出 “日志脱敏完整性”。 |
| **硬编码阈值导致业务回归** | 引入 **配置审查** 步骤：每次提交前搜索硬编码数字，要求提供配置来源或注释解释。 |
| **增量审查容易漏掉全局一致性** | 在增量审查结束后执行一次 **全局一致性脚本**（例如检查所有 `sanitize()` 调用、异常日志统一性），确保不因只看增量而遗漏全局规则。 |
| **HTTP 明文依赖的技术债务** | 将该类风险列入 **技术债务清单**，并在每次发布时审计是否有新入口导致明文依赖。 |
| **早 EOF 与 fallback 冲突** | 在业务实现前先绘制 **状态转移图**，明确每个异常路径的触发条件，避免不同路径之间的阈值冲突。 |
| **测试覆盖率不足的异常路径** | 为每个 `catch` 分支编写 **异常单元测试**（使用 Mockito/PowerMock 模拟异常），并在 CI 中强制要求覆盖率 ≥ 90%。 |

## 5. 增量审查反思  

| 项目 | 结果 | 说明 |
|------|------|------|
| **是否解决了之前审查提出的问题** | ✅ 大部分已修复：EOF 截断、缓存失效、FailureCode、日志注入、latch 释放、流恢复位置等均已实现。 |
| **是否引入了新的风险** | ⚠️ 新增了 **明文 HTTP 重定向** 风险、**早 EOF‑fallback 240 s** 误判风险、**硬编码阈值**（重试次数、间隔）以及 **日志脱敏不完整**（onClientFailure）三个新风险点。 |
| **审查覆盖度是否因只看增量而下降** | 有所下降：审查主要聚焦在本次改动文件，未系统性检查 **MusicCache** 并发安全、**ModNetwork** 的异常日志统一性、以及全局 `HttpClient` 配置。若只看增量，容易遗漏这些跨文件的全局一致性问题。 |

**改进建议**  

1. **增量审查后补全全局检查**：在完成增量审查后，跑一次全项目的规则扫描（如日志脱敏、异常日志、阈值配置），确保没有因增量而遗漏的全局问题。  
2. **风险分层评估**：对每个新增风险进行 **风险等级划分**（Minor / Major / Critical），并在 PR 中附上对应的 **后续任务**（如在下一个里程碑中统一 HTTP scheme 校验）。  
3. **变更影响评估**：在审查前先绘制 **影响矩阵**（改动文件 ↔ 受影响模块），确认是否有跨模块的副作用（如 `MusicServerBridge` 的日志脱敏、`MusicApiClient` 的重定向策略）。

**结论**：本次审查在发现并验证关键功能修复方面表现出色，提供了有价值的后续改进建议。但增量审查的范围限制导致对全局一致性（日志脱敏、异常日志、阈值配置）以及新引入的安全风险（明文 HTTP）检查不够深入。建议在后续审查流程中加入全局规则扫描与风险分层评估，以提升审查的覆盖度和前瞻性。
