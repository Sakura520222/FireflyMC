# 代码审查深度反思

## 1. 审查质量评估

**覆盖度：增量充分，全局视角缺失**
- 对增量部分（单行括号添加）的审查是完整且准确的
- 但审查摘要仅用一句话带过"安全相关 major 问题不在范围内"，未量化说明还有多少问题悬而未决，可能导致后续审查者或合并者产生**虚假安全感**

**准确度：评分语义存在歧义**
- 9/10 作为**增量评分**是合理的——这个提交本身无可挑剔
- 但结合历史上下文（PR 仍有 3 个 major 未解决），这个数字可能被误读为"PR 整体质量 9 分"
- **误判风险**：approve 决策的粒度不够精确，未区分"增量可合并"与"PR 可合并"

**完整性：意图理解正确**
- 准确识别出这是纯粹的可读性优化，语义等价
- 正确判断无副作用

## 2. 发现的模式

**代码模式**：
- 开发者对审查意见的响应精准——只改被指出的问题，不做无关变更，这是良好的修复习惯
- 显式括号的使用意愿存在，但初始编写时容易忽略，说明需要 lint 规则辅助

**架构观察**：
- `SingleplayerRelayControlScreen` 在依赖图中处于扇出高位（依赖 5 个类），且被频繁标记问题（ULA 过滤、代码重复、可读性），**疑似正在演化为上帝类**
- IPv6 探测结果（`Ipv6ProbeResult`）直接被 UI 层消费，缺少中间转换层

## 3. 规范完善建议

### 建议新增规则

| 规则 | 说明 |
|------|------|
| **增量评分必须附带整体健康度** | 当 PR 存在未解决 major 时，评分格式应为 `9/10 (增量) · 整体: 3 major 待解决` |
| **approve 决策分级** | 区分 `incremental-approve`（增量可合入）与 `pr-approve`（PR 可合并），存在 major 时只能给前者 |
| **布尔表达式强制括号** | 含 `&&` 和 `||` 混合的表达式，必须用括号显式分组，纳入 checkstyle |

### 项目特有规范

- **UI 层数据过滤职责**：Screen 类展示网络地址时，必须在数据绑定层完成 ULA/link-local 过滤，不应在渲染逻辑中分散处理

## 4. 经验教训

1. **评分数字的传播风险**：增量审查的高分会在 PR 历史中"漂白"低分轮次，建议评分系统改为"增量分数 + 累计分数"双轨制

2. **微小变更的审查价值**：单行括号变更的审查本身价值有限，真正的价值在于**确认历史问题跟踪状态**——这次审查在这个维度上做得不够

3. **quick 模式的摘要模板缺陷**：当前模板允许用"不在范围内"一笔带过历史问题，应改为强制列出：
   ```
   ## 未解决历史问题
   - [major] 隐私默认值 (第1轮) — 预计本轮不修复
   - [major] ULA 过滤 (第1轮) — 预计本轮不修复
   - [major] 测试线程泄漏 (第1轮) — 预计本轮不修复
   ```

## 5. 增量审查反思

**问题解决情况**：
- ✅ 精确修复了第1轮的括号可读性问题，无过度修复

**新风险引入**：
- ❌ 无新风险

**覆盖度下降分析**：
- 增量部分覆盖度 100%
- **但整体感知覆盖度下降**：quick 模式的"隧道视野"在本轮体现为——审查者知道问题存在，但选择了不强调。根据项目记忆中"增量审查隧道视野"的总结，这恰好是被预警过的模式，说明该模式仍然没有被有效对抗

**核心反思**：
> quick 模式下，审查者的注意力天然聚焦于 diff。当 diff 是"正确但微小"时，审查容易变成形式确认。此时的审查价值不在于验证 diff，而在于**维持对 PR 整体状态的可见性**。本轮审查在前者上合格，在后者上失职。
