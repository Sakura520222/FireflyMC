# 深度反思：PR #57 AI 模块重构

## 1. 审查质量评估

### 覆盖度：存在明显盲区

本次审查对 `AgenticToolLoop` 核心逻辑的挖掘很深，tool_calls 截断一致性问题是高质量发现。但**大面积变更文件被完全跳过**，严重违反增量审查的完整性要求：

| 文件 | 变更量 | 审查评论数 | 风险 |
|------|--------|-----------|------|
| `ClearDroppedItemsFunctionTool.java` | **+111 (全新文件)** | **0** | 新攻击面：谁可触发？范围校验？速率限制？ |
| `GiveItemFunctionTool.java` | +149/-49 | **0** | 大幅扩展，物品参数注入风险未检 |
| `FunctionToolHelper.java` | +80/-185 | **0** | 删除 185 行，是否丢失安全校验？ |
| `AIChatEventHandler.java` | +48/-238 | **0** | 删除 238 行，事件处理防线是否削弱？ |
| `ServerConfig.java` | +27/-6 | **0** | 新增 5 个配置项，未做生命周期审查 |
| `AIConfig.java` | +45/-72 | **0** | 配置默认值、边界值未逐项验证 |

**结论**：审查者陷入了"核心新类深度挖掘 + 其余文件盲飞"的模式，6 个有实质风险的文件零覆盖。

### 准确度：存在规范执行偏差

- **Major 判定准确**：tool_calls/tool_result 数量不一致确实会导致 OpenAI API 拒绝请求，且在超限边界条件下必触发，判定合理。
- **Minor 判定与规范矛盾**：规范速查表明确写着 **"Javadoc 约束违反：字段 Javadoc 声明行为被违反时至少 major"**，但 `sanitizeMessage` 的 Javadoc 过时被标为 minor。要么规范过严需要降级，要么审查者未查阅规范表——两者都有问题。
- **Suggestion 严重度可能偏低**：`CompletableFuture` 链无异常兜底，结合项目规范"网络请求禁止静默丢弃"和"所有异步等待必须设置超时"，这更应该是 minor 甚至 major，而非 suggestion。

### 完整性：对删除代码缺少安全审计

238 行从 `AIChatEventHandler` 移除、185 行从 `FunctionToolHelper` 移除、230 行整个 `ClearInventoryFunctionTool` 删除。审查未回答关键问题：**这些被删除的代码中是否包含输入校验、权限检查、错误处理逻辑？是否已迁移到新位置？** 这是删除类变更的标准审查动作，完全缺失。

## 2. 发现的模式

### 代码模式
- **ToolContext 统一上下文模式**：用单一上下文对象替代 `(ServerPlayer, MinecraftServer)` 双重载，消除重复代码——这是本 PR 最有价值的架构改进。
- **双层限流模式**：`maxToolRounds`（轮次）+ `maxToolCalls`（总调用数）双重上限，设计合理。
- **配置驱动功能开关**：`aiDisabledTools` 禁用名单、`aiParallelToolCalls` 并行开关，符合项目"配置全生命周期审查"要求（但未实际审查）。

### 架构观察
- AI 模块架构质量**显著高于**网络模块（对比 `RelayLobbyWebSocketClient`、`P2PConnectionManager` 的持续溃烂），说明不同模块的开发者能力或投入差异很大。
- 工具注册表 + 统一上下文 + Agent 循环的三层结构是标准的 AI Agent 架构，方向正确。

## 3. 规范完善建议

### 新增规则

| 规则 | 说明 | 触发条件 |
|------|------|---------|
| **OpenAI 协议一致性** | `tool_calls` 数组与 `tool` 角色消息必须严格一一对应，任何截断/过滤操作必须同时作用于两者 | 涉及 OpenAI tool calling 的代码 |
| **大变更文件强制覆盖** | 单文件变更 >80 行（含删除）必须至少 1 条审查评论 | 所有 PR |
| **删除代码安全迁移审计** | 删除 >50 行时，必须确认其中安全校验/错误处理已迁移至新位置 | 含大量删除的 PR |
| **新增文件审查底线** | 全新文件 >50 行必须审查：输入校验、权限控制、异常处理 | 新增文件 |
| **AI 工具攻击面审查** | 每个 AI FunctionTool 必须审查：调用权限、参数注入、速率限制、影响范围 | AI 模块工具类 |

### 修改规则

- **Javadoc 规则降级为 minor 起步**：当前"至少 major"过于严苛，`sanitizeMessage` 这种非安全相关的文档过时标 major 不合理，改为"安全相关 Javadoc 违反至少 major，其余 minor"。
- **异步异常兜底升级**：从 suggestion 提升为 minor，明确 `CompletableFuture` 链必须有 `.exceptionally()` 或 `.whenComplete()`。

## 4. 经验教训

### 截断一致性问题——可泛化的审查模式
`tool_calls` 截断但历史消息未同步截断，本质是**"同一数据源的多个消费者未同步更新"**。这和"日志脱敏全级别覆盖"是同一模式：修改了数据的某个视图，遗漏了其他视图。审查时应主动搜索：**这个变量还在哪里被使用？**

### 配置删除的连带清理
移除 `aiMaxResponseLength` 时，遗漏了 Javadoc、可能还有配置文件注释、wiki 文档等。**配置删除应像配置新增一样做全链路扫描**。

### AI 工具是新的攻击面
AI 决定调用哪个工具、传什么参数，本质上是**把命令执行权交给了一个不可信的决策者**。每个 FunctionTool 都应被视为"公开 API 端点"来审查——参数校验不能依赖"AI 不会传错"，而必须自身防御。

## 5. 增量审查反思

### 新增提交是否解决历史问题？
本次 PR 聚焦 AI 模块，与历史 major 问题（ModNetwork、ClientState、ClientPayloadHandler）无交集，正确标注为"不在 diff 范围"。但**历史问题已跨多个 PR 累积 4 个未修复 major**，应触发"连续降分触发机制"或至少在决策中体现——当前评分 6 分与 4 个持续 major 并存，评分未充分反映技术债。

### 增量变更引入的新风险
- **tool_calls 截断 bug**：新引入的 major，边界条件必触发
- **ClearDroppedItemsFunctionTool**：全新攻击面，零审查
- **AIChatEventHandler 删除 238 行**：可能丢失防御逻辑，零审查
- **GiveItemFunctionTool 扩展 149 行**：物品参数注入面扩大，零审查

### 覆盖度下降分析
本轮典型的**"焦点偏食"**：AgenticToolLoop 占了审查者 90% 的注意力（确实值得深挖），但导致其余 60% 的变更行数完全裸奔。增量审查的标准动作是"看 diff 验逻辑，扫上下文防遗漏"——本次只做了前半句。

**改进方案**：增量审查应增加**文件覆盖检查清单**——提交评论前，逐文件勾选"已审查/无需审查（说明原因）"，防止大文件静默跳过。

---

**总结**：本轮审查在深度上表现优秀（tool_calls 一致性问题发现精准），但在广度上严重失衡。6 个变更量 >50 行的文件零覆盖，其中包含全新攻击面和大面积删除，这是增量审查模式下最危险的盲区。建议下轮补充审查这些文件，特别是 `ClearDroppedItemsFunctionTool` 和 `AIChatEventHandler` 的删除内容。
