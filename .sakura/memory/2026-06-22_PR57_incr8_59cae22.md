# 代码审查深度反思 — PR #57 增量审查

## 1. 审查质量评估

### 覆盖度：增量充分，但存在结构性盲区
- 新增的 3 个提交覆盖到位，精准定位了 `RemoveEntitiesFunctionTool` 的两个逻辑缺陷和一个性能隐患
- **遗漏点**：代码清理提交（c9b182da）涉及 17 个文件，审查仅一笔带过"移除无用导入和字段"。虽然清理类变更风险低，但大规模删除应至少抽样验证——例如 `PlayerPasswordManager` 删除 `loaded` 字段后，原有的懒加载语义是否被其他机制替代？`TitleManager` 同理。未验证就放行存在隐性回归风险

### 准确度：严重程度判定合理
- 过滤失效 → minor ✓（逻辑错误但非安全漏洞，AI 输入非法字符概率低）
- entity_id 无距离约束 → minor ✓（功能与描述不符，但不构成安全风险，因为 AI 本身难以构造远距离 entity_id）
- 结果上限 → suggestion ✓（性能问题而非正确性问题）
- 遗留 3 个 major 维持不动 ✓

### 完整性：理解到位但未追问根因
- 审查准确识别了 AI 工具的设计意图
- **不足**：AIApiClient 超时从 `10s/15s` 改为 `90s/120s`，PR 描述声称"修复配置问题"，实际是从一个硬编码变为另一个硬编码。审查标记了 suggestion，但**未指出 PR 描述与实现严重不符**——这属于描述欺骗，应至少 minor

## 2. 发现的模式

### 代码模式
- **硬编码惯性**：超时值、结果上限均硬编码，开发者倾向于"先跑通再配置化"，但"再"从未发生
- **AI 工具防御性编程缺失**：两个新工具均未在入口做参数白名单校验，而是依赖下游 `tryParse` 返回 null 后静默降级——这是"隐式失败"模式
- **破坏性操作与查询操作同等对待**：`RemoveEntitiesFunctionTool` 和 `GetNearbyEntitiesFunctionTool` 使用相同的实现范式，没有为破坏性操作增加额外的安全层

### 架构观察
- AI FunctionTool 架构是新引入的，目前缺乏统一的：
  - 参数校验框架（每个工具自行实现，容易遗漏）
  - 结果截断机制
  - 破坏性操作的安全策略
- 这解释了为什么两个工具同时出现"缺少上限"和"缺少校验"的同类问题

## 3. 规范完善建议

### 新增审查规则

| 规则 | 说明 | 级别 |
|------|------|------|
| AI 工具破坏性操作安全链 | 删除/修改类 FunctionTool 必须具备：(1) 参数白名单校验，非法输入显式报错而非静默降级；(2) 操作结果必须包含受影响数量；(3) 工具描述中的约束必须在代码中强制执行 | major |
| AI 工具结果强制截断 | 所有查询类 FunctionTool 必须设置硬性结果上限（建议 ≤50 条），超限须截断并提示"结果已截断" | major |
| 工具描述-实现一致性 | FunctionTool 的描述中声明的参数约束（如 radius 范围、entity_id 作用域）必须与实现完全一致，不一致为 minor | minor |
| PR 描述真实性 | PR 描述声称修复 X 问题但实现未解决 X，属于描述与实现不符，至少 minor | minor |
| 清理类提交抽样验证 | 涉及 ≥10 文件的删除/清理提交，必须至少对核心模块（认证、网络、状态管理）的变更做语义验证 | suggestion |

### 修改现有规则
- **"安全机制失效默认 major"** 应扩展覆盖 AI 工具场景：`RemoveEntitiesFunctionTool` 的过滤静默失效本质上是安全机制失效（防御层被绕过），当前标 minor 偏轻。建议补充：*"AI 工具中涉及实体/方块修改的过滤条件失效，按 major 处理"*

## 4. 经验教训

### 值得关注的要点
1. **"修复"类提交的真实性验证**：不能只看 diff 改了什么，还要看 PR 描述的"修复了什么"是否真正被修复。本次超时"修复"就是典型——改了值但没有解决"不可配置"这个根本问题
2. **AI 工具需要独立审查清单**：作为新引入的架构模式，不能沿用普通方法的审查标准。AI 工具的特殊风险点：参数来自 LLM 幻觉（不可控输入）、结果返回 LLM 上下文（有大小限制）、操作直接影响游戏世界（破坏性）
3. **同类问题应批量指出**：两个工具同时缺少"结果上限"类防护，审查应合并为一条模式问题并要求统一解决，而非分别在两个文件各标一条 suggestion

### 技术经验
- `ResourceLocation.tryParse()` 返回 null 是 Minecraft mod 开发中常见的"静默失败点"，任何依赖它的分支都必须处理 null 情况，且对于破坏性操作必须走"拒绝"路径而非"跳过过滤"路径

## 5. 增量审查反思

### 遗留问题解决情况：零进展
3 个遗留 major 问题（ModNetwork 空 catch、lockoutMinutes 范围校验、currentServerIp volatile）在本轮**完全未被触碰**。这已是 3+ 轮未修复。

**关键反思**：增量审查模式正在被"稀释策略"利用——开发者通过持续添加新功能提交，使每轮审查的注意力被增量内容占据，遗留问题的紧迫感被稀释。当前策略（每轮提及但仅建议"优先处理"）已经失效。

**建议调整**：
- 当同一 PR 存在 ≥3 轮未修复的 major 时，增量审查应**拒绝审查任何新增功能**，仅接受遗留问题的修复提交
- 或在 PR 级别设置"遗留 major 阻断阈值"：≥2 个未修复 major 时，新提交直接 request_changes 不做详细审查

### 新增风险
- `RemoveEntitiesFunctionTool` 引入了可被 AI 误触发的破坏性操作，但审查给出的 minor/suggestion 级别是合理的——实际利用难度高（需要 AI 同时产生幻觉且玩家确认）
- 真正的风险在于**模式扩散**：如果这两个工具的校验缺失不被纠正，后续新增的 AI 工具会复制同样的模式，形成系统性缺陷

### 覆盖度下降
增量审查天然丢失全量视角：
- `ServerConfig` 的 `defineListAllowEmpty` 修改仅一句话带过，未验证：改为允许空列表后，下游消费该配置的代码是否正确处理了空列表？是否会导致 NPE 或空循环？
- 17 个文件的导入清理，无法确认是否有"删掉了实际在用的导入但编译器还没报错"的情况（比如反射引用的类）

## 总结

本轮审查在增量范围内质量合格，但暴露了**增量审查策略在长期 PR 中的治理失效**问题。最核心的改进不是审查技术本身，而是**审查流程的阻断机制**——当遗留 major 积压到阈值时，必须强制停止新功能摄入，否则审查将陷入"永远在追新问题，永远不解决老问题"的死循环。
