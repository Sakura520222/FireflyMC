**二、发现的模式**

| 类别 | 观察到的模式 |
|------|--------------|
| **编码习惯** | 1. 大量 **catch‑all**（`Throwable`）包装，虽保证不泄漏但掩盖了根本错误类型。<br>2. **CompletableFuture.join()** 被直接使用，缺少超时包装，违背项目 “P2P 超时强制兜底”。<br>3. **HttpClient** 实例在 `MusicApiClient` 中每次请求重新构造，未复用，增加资源开销。 |
| **异常处理** | 多处在 **finally** 中直接调用 `failRequest()`，但未记录异常细节，违背 “网络请求禁止静默丢弃”。 |
| **并发模型** | `SearchSession` 从 `Map` 改为 `ArrayDeque`，实现了 **FIFO** 并发控制，但仍缺少 **volatile**/`Atomic*` 标记，跨线程可见性未保证。 |
| **资源清理** | 引入 **.part** 文件清理、`TeeInputStream.isBranchBroken()` 检查，表现出对 **I/O 泄漏** 的关注。 |
| **架构特征** | 1. **客户端‑服务器双向状态机**：服务器端 `MusicQueueManager` 负责权威调度，客户端 `MusicPlaybackManager` 负责本地容错。<br>2. **链路驱动**：从指令 → API → 下载 → 播放 → HUD，层次清晰。<br>3. **测试驱动**：新增单元测试覆盖率提升，但仍缺少 **集成/端到端** 场景（如跨玩家同步播放）。 |

**三、规范完善建议**

1. **安全传输规则**  
   - **新增规则**：`HttpClient.Redirect.NEVER` 为默认，除非业务明确允许跨协议。若必须允许，必须在请求完成后检查 `uri.getScheme()`，非 `https` 时记录 `WARN` 并中止播放。  
   - **检查点**：所有 `HttpClient` 创建位置（尤其是 `MusicApiClient`）必须通过专用工厂方法 `HttpClientFactory.secureClient()`。

2. **异常日志规范**  
   - **新增规则**：`catch (Throwable e)` 必须在捕获后 **统一记录**（使用 `log.error("...", e)`），禁止空 catch 或仅 `failRequest()`。  
   - **审查点**：`MusicCommandHandler`、`MusicPlayer`、`MusicApiClient` 中的所有 catch 块。

3. **CompletableFuture 超时强制**  
   - **规则强化**：所有 `join()` 必须配套 `orTimeout`，或使用 `get(timeout, TimeUnit)`。若业务已有内部 watchdog，仍需在调用点显式声明，便于审计。  
   - **工具**：提供 lint 检查 `FutureJoinWithoutTimeout`。

4. **HttpClient 实例复用**  
   - **规则**：项目中每个模块只能持有 **单例** `HttpClient`，禁止在方法体内 `HttpClient.newHttpClient()`。  
   - **审查点**：`MusicApiClient` 中的 `client` 字段应在构造函数一次创建，后续请求共用。

5. **跨线程可见性**  
   - **规则**：所有跨线程共享的非 `final` 字段必须声明 `volatile` 或使用 `Atomic*`，并提供 `reset()` 方法。  
   - **审查点**：`SearchSession.id`、`MusicQueueManager.pendingSessions`（已改为 `ArrayDeque`，但仍需同步/volatile）。

6. **日志脱敏统一入口**  
   - **规则**：同一数据源（如歌曲名称、玩家 ID）在不同日志级别必须使用同一脱敏函数 `logSafe()`。审查时检查新增日志是否遵循。  

**四、经验教训**

| 教训 | 具体表现 | 对策 |
|------|----------|------|
| **安全隐患易被忽视** | HTTPS→HTTP 重定向跨了三轮仍未解决，说明审查者对 **传输层安全** 关注不足。 | 在审查清单里加入 “网络协议安全检查” 项，优先审视 `HttpClient.Redirect` 配置。 |
| **增量审查的视野局限** | 只聚焦本次 diff，未回顾 `MusicApiClient` 之前的 **HttpClient 重用** 与 **异常记录**。 | 增量审查后进行 **回顾模式**：检查本次修改是否触及已有风险点的“同类缺陷”。 |
| **异常捕获的双刃剑** | 大量 catch‑all 防止了泄漏，但也隐藏了根因，导致后续调试成本上升。 | 推荐使用 **细粒度异常**（`IOException`, `InterruptedException`）并在 `catch` 中记录完整堆栈。 |
| **测试覆盖的误区** | 单元测试覆盖率提升，但仍缺少 **并发/时序** 场景（如多个特权玩家并发搜索）。 | 引入 **并发压力测试**（使用 `ExecutorService` 模拟多玩家）并将其纳入 CI。 |
| **资源清理的主动性** | 本次加入 `.part` 清理、分支破损检测，显著降低磁盘泄漏风险。 | 将 **资源清理模式**（文件残留、流分支）列入项目代码规范，所有 I/O 类必须提供 `cleanup()`。 |

**五、增量审查反思**

| 维度 | 评价 |
|------|------|
| **问题闭环** | 本轮增量基本 **解决了之前审查指出的 8 项核心缺陷**（异常泄漏、读取挂起、并发会话、缓存破损、VBRI 越界、时钟降级、残留 `.part`、重试策略），闭环效果良好。 |
| **新风险** | 1. **HTTPS→HTTP 重定向** 仍未修复，属于 **安全回退**。<br>2. **join() 超时缺失** 仍为潜在阻塞点，虽已有 watchdog，但缺少调用点的显式防御。<br>3. **HttpClient 实例复用** 未在本次增量中处理，仍可能导致资源浪费。 |
| **覆盖度下降** | 因只审查增量，未对 **旧代码中已有的全局异常记录、日志脱敏** 再次核实，导致这些潜在缺陷未被捕获。建议在每次增量审查后，进行一次 **“同类缺陷回溯”**（即搜索项目中相同模式的代码并统一检查）。 |
| **整体建议** | - 在增量审查结束后，执行 **风险回顾脚本**（搜索 `Redirect.ALWAYS`、`catch (Throwable)`、`join()`），确保未因关注局部而遗漏全局风险。<br>- 将 **安全传输**、**异常日志**、**CompletableFuture 超时** 三项列入 **必检清单**，形成审查模板。 |

**结论**  
本次审查在 **功能稳健性** 上取得显著进步，成功闭环了多项关键缺陷。但 **安全传输** 与 **显式超时** 两大方向仍需在后续迭代中强制落实。通过完善审查规则、引入同类缺陷回溯以及加强并发/安全测试，可进一步提升代码质量和审查的覆盖完整度。
