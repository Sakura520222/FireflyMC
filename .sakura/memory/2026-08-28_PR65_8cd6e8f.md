## 2. 发现的模式  

### 2.1 代码模式  

| 模式 | 现象 | 影响 |
|------|------|------|
| **“先 finalize 再返回 RETRY”** | `finally` 中提前落盘，导致半截文件被当作完整缓存。 | 产生长期错误缓存，影响后续播放。 |
| **日志直接拼接用户可编辑字段** | `song.title()`、`requesterName()`、玩家名直接写入日志。 | 潜在日志注入、信息泄露风险。 |
| **枚举 ordinal 作为协议字段** | `FailureCode.ordinal()` 直接用于网络传输。 | 版本兼容性风险，序号变动会导致语义错位。 |
| **容错阈值硬编码** | `EARLY_EOF_TOLERANCE_MS = 3_000`。 | 对 VBR 曲目误判率高。 |
| **异常分支空实现** | `reportFinal` 中对 `RETRY` 的空分支。 | 错误被吞掉，难以定位。 |
| **跨线程状态未同步** | `MusicCache` 通过 LRU 直接删除，未在多线程环境加锁。 | 潜在并发竞争（虽未出现但属于隐患）。 |
| **单元测试仅覆盖单人/多人场景** | 未覆盖异常路径（半截缓存、日志脱敏）。 | 代码回归风险增大。 |

### 2.2 架构观察  

1. **播放链路高度耦合**：`MusicPlayer`、`MusicCache`、`JavaSoundOutput`、`MusicServerBridge` 之间通过大量共享对象和直接调用形成紧耦合，导致单点改动会波及多层。  
2. **错误码层级划分**：通过 `FailureCode` 将网络错误、流错误、解码错误区分，思路清晰，但实现方式（ordinal）破坏了向后兼容的安全边界。  
3. **缓存策略**：使用文件系统 + LRU 256 MB 限制，缺少对缓存完整性的校验（如 MD5、文件长度校验），导致半截文件被误当作完整缓存。  
4. **日志体系**：项目已有统一脱敏入口，但新代码未遵循，说明日志规范的渗透力度不足。

## 3. 规范完善建议  

### 3.1 新增/修改审查规则  

| 规则 | 建议内容 | 适用范围 |
|------|----------|----------|
| **缓存完整性校验** | 在 `finalizePartFile` 前必须校验文件长度或校验和，未通过则删除或标记为 “损坏”。 | `MusicCache`、`MusicPlayer` |
| **异常分支不可空** | 所有 `catch`/`else`/`switch` 中的 `RETRY`、`FAIL` 分支必须显式记录日志、上报或清理资源。 | 全项目异常处理 |
| **日志脱敏强制** | 所有日志输出涉及用户可编辑字段必须走统一的 `logSafe(String)` 方法；审查时检查同文件中不同日志级别是否统一使用该方法。 | `src/main/java/**/log*`、`MusicServerBridge` |
| **枚举序列化安全** | 禁止直接使用 `ordinal()` 进行网络传输；若必须使用，必须在每次枚举变更时同步提升 `ModNetwork.NETWORK_VERSION`，并在审查中检查该同步。 | `FailureCode`、所有 Payload |
| **容错阈值配置化** | 将 `EARLY_EOF_TOLERANCE_MS`、`RETRY_COUNT`、`RETRY_DELAY_MS` 等阈值抽取为可配置项（`config`），并在审查中验证其默认值与业务需求匹配。 | `MusicPlayer`、`JavaSoundOutput` |
| **缓存写入结果类型化** | 引入 `CacheWriteResult { SUCCESS, INCOMPLETE, FAILED }`，并在 `streamAttempt` 返回该结果，审查时检查对 `INCOMPLETE` 的处理是否删除缓存。 | `MusicCache`、`MusicPlayer` |
| **单元测试覆盖要求** | 对每条异常路径（半截缓存、日志脱敏、枚举不匹配）必须至少提供一个单元测试，用 `@ParameterizedTest` 验证不同分支。 | `src/test/**` |
| **跨线程资源同步** | 对任何跨线程共享的文件/缓存对象必须使用 `synchronized`、`ReentrantLock` 或 `Concurrent` 结构，并在审查中检查是否缺失。 | `MusicCache`、`MusicPlayer` |
| **日志注入防护** | 所有日志字段在写入前需调用 `StringUtils.escapeControlChars()`（或等价实现），审查时搜索 `\n`、`\r` 出现的未处理日志。 | 全日志点 |

### 3.2 项目特有的规范要点  

1. **播放链路错误码统一声明**：在 `FailureCode` 注释中明确每个枚举对应的业务语义、是否投 quorum、是否可恢复。  
2. **缓存路径统一管理**：所有缓存文件路径应统一通过 `MusicCache.getCacheDir(songId)` 获取，禁止硬编码路径。  
3. **重试机制统一实现**：提供 `RetryPolicy` 工具类（包含次数、间隔、退避策略），供 `JavaSoundOutput.tryOpen()`、`MusicPlayer.streamAttempt()` 等复用，避免在不同文件中出现散落的硬编码。

## 4. 经验教训  

| 经验点 | 建议的审查关注点 |
|--------|----------------|
| **半截缓存落盘会产生长期错误** | 审查涉及 `finally`、`try‑with‑resources` 的代码时，先确认资源释放顺序是否与业务注释保持一致。 |
| **异常路径的“沉默”是隐蔽危机** | 对每个 `catch`、`else`、`switch` 分支检查是否有日志、上报或清理操作；尤其是 `RETRY`、`FAIL` 分支。 |
| **日志脱敏是全链路安全的底线** | 只要出现 `logger.info/warn/debug` 输出外部可控字符串，即标记为 **major**（除非已走统一脱敏入口）。 |
| **枚举序列化必须兼容** | 当发现 `enum.ordinal()` 用于网络协议时，立刻检查版本号同步及向后兼容策略。 |
| **容错阈值应考虑业务多样性** | 对于媒体播放类项目，使用硬编码的时间阈值容易在 VBR/CBR、不同码率等场景下失效，审查时应要求配置化或基于实际测算的动态阈值。 |
| **单元测试要覆盖异常分支** | 新增功能的同时，审查测试文件是否覆盖了异常、边界、恢复路径；缺失时直接提出 **major** 建议。 |
| **跨模块改动需要链路审视** | 本次 PR 改动涉及 `MusicPlayer`、`MusicCache`、`MusicServerBridge` 多个模块，审查时要从“请求 → 网络 → 缓存 → 播放 → 反馈”完整链路检查一致性。 |
| **代码注释与实现必须保持一致** | `MusicPlayer` 中的注释明确指出 “避免半截音频被缓存落盘”，但实现相反，这类不一致是高危信号，必须在审查中标记并要求修正。 |
| **重构后要回顾旧的安全/性能检查** | 大幅重构后，审查者需要回顾项目已有的安全检查清单（日志脱敏、并发安全、缓存完整性），防止旧规则被遗漏。 |

### 小结  

本次审查已经很好地捕捉了几项关键风险（半截缓存、日志注入、枚举兼容），但可以在以下方面提升：

1. **结构化风险汇总**：在审查报告中加入风险矩阵（影响范围 × 严重度），帮助评审快速定位最高优先级问题。  
2. **测试覆盖度检查**：对异常路径的单元测试进行强制检查，确保回归安全。  
3. **统一规范渗透**：通过代码模板或 IDE 检查插件强制使用日志脱敏、缓存写入结果等规范，降低人工遗漏概率。

通过上述改进，后续的全量审查将更具系统性、可追溯性，也能更好地保障项目的稳定性与安全性。祝后续修复顺利！
