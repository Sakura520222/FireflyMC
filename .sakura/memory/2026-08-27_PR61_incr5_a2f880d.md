## 深度反思报告

### 1. 审查质量评估

*   **覆盖度 (8/10)**：
    *   **核心问题捕获精准**：成功识别出 `PacketDistributor.sendToServer` 在非主线程（虚拟线程）调用的严重线程安全隐患，这是 Minecraft/Forge 网络层开发的高频雷区。
    *   **防御深度不足**：敏锐地指出了关键字长度截断的“纵深防御”缺失，虽然命令层有检查，但在 Payload 构造前再次截断符合安全最佳实践。
    *   **潜在遗漏**：
        *   **并发控制**：`MusicProxySearchClient.handle` 中直接启动虚拟线程，若服务端因网络抖动连续向同一客户端发送多个请求，是否会瞬间创建大量虚拟线程？审查未提及对同一 `sessionId` 或并发请求的节流或去重逻辑（尽管服务端有 `deadlineNs`，但客户端的“启动”动作缺乏守门）。
        *   **资源清理**：虚拟线程内部抛出异常时，是否有明确的错误处理和日志记录？目前仅指出了发送线程问题，未关注异常分支的日志脱敏要求（参考项目记忆中的“日志脱敏完整性”）。

*   **准确度 (9/10)**：
    *   **定级合理**：将跨线程发包标记为 `major` 完全正确，这可能导致连接状态不一致或数据包丢失甚至崩溃。关键字截断定为 `minor` 也恰如其分，属于防御性编程范畴。
    *   **无误判**：指出的问题均有代码依据，且与项目既有的“单线程 executor 禁止 join”、“组合操作原子性”等并发约束精神一致。

*   **完整性 (9/10)**：
    *   充分理解了“服务端无外网 -> 客户端代搜 -> 结果回传”的降级链路意图。不仅关注了功能实现，还关注了服务端对回包的防御性校验（`isValidSongId` 等），理解较为全面。

### 2. 发现的模式

*   **代码模式**：
    *   **异步滥用**：开发者倾向于使用虚拟线程（`Thread.ofVirtual()`）处理异步任务，但对“必须切换回主线程进行 MC 操作”这一核心约束缺乏敏感度。这种“在线程中直接发包”的模式与项目早期 `SingleThreadExecutor` 中阻塞的问题同源，即**线程边界混淆**。
    *   **防御性编程分层**：服务端代码表现较好（如回包校验、Clamp），但客户端代码倾向于信任输入或环境（如直接使用 Payload 传来的参数）。

*   **架构观察**：
    *   **Client-Server 角色反转**：本次变更引入了“Server request -> Client action -> Server response”的反向交互模式。这种模式增加了系统的复杂性，客户端从单纯的指令执行者变成了具有外部网络能力的 Worker。架构上要求客户端必须有更严格的异常处理和超时控制，以防止客户端故障拖垮服务端逻辑（虽然服务端有 `deadlineNs`，但若客户端一直不回包，服务端会话会一直占用直到超时）。

### 3. 规范完善建议

*   **新增/修改规则**：
    *   **网络发包主线程强制化**：明确规定所有 `PacketDistributor.sendToServer()` 或 `ClientPacketSender.send()` 调用**必须**包裹在 `Minecraft.getInstance().execute(...)` 或主线程检查块中。任何网络回调线程/虚拟线程直接发包均为 `major` 缺陷。
    *   **虚拟线程资源控制**：新增规则：禁止在 Handler/Callback 中无限制地 `Thread.start()`。对于高频触发的事件处理，必须使用有界队列或复用线程池，防止虚拟线程数量爆炸。

*   **项目特有规范**：
    *   **Payload 数据一致性**：当 Payload 的 Codec 容量（如 32767）大于业务逻辑限制（如 256）时，必须在**数据出口处**（构造 Payload 前）进行截断，而不仅仅是在入口处校验。

### 4. 经验教训

*   **技术要点**：
    *   **虚拟线程不是万能药**：在 Minecraft 这种强单线程模型（游戏循环/网络事件循环）中，虚拟线程仅适用于阻塞 IO（如 HTTP 请求），绝不能绕过主线程去操作游戏状态或发送数据包。
    *   **代理模式的信任边界**：在“客户端代理”场景下，服务端必须将客户端视为“不可信输入源”。本次审查中服务端做得较好，未来应保持这种“回包即外部输入”的警惕性。

*   **审查关注点**：
    *   对于涉及“反向请求”或“代理执行”的代码，重点检查**超时清理**是否覆盖了客户端无响应的所有场景（如客户端崩溃、强制退出）。
    *   任何新增的 `Thread.ofVirtual()` 或 `Executor.submit` 都应触发审查对“生命周期”和“异常捕获”的警觉。

### 5. 增量审查反思

*   **问题解决情况**：
    *   本次是功能新增（`feat`），而非修复之前的 `major` 问题。之前的“HTTPS 降级”问题依然存在，并未在本轮 PR 中解决。这提醒在 `feat` 类 PR 中，也要关注是否顺手修复了模块内的遗留技术债，或者是否引入了新的架构复杂性。

*   **新引入的风险**：
    *   引入了客户端作为 HTTP 代理的风险。虽然服务端有校验，但客户端发起 HTTP 请求的频率控制（防刷）依赖于玩家手动输入，目前看风险可控，但未来若需自动化代理，需增加限流。

*   **覆盖度评估**：
    *   增量审查集中在新文件 `MusicProxySearchClient` 和 Payload 上，覆盖度良好。
    *   但对于 `MusicQueueManager` 的修改（`SearchSession` 增加 `deadlineNs`），仅关注了 Javadoc 格式，未深入审查 `tick()` 中 `expireStalePendings()` 的实现逻辑是否真的能防止内存泄漏（虽然摘要说有，但未深入验证时间计算逻辑是否准确）。这在增量审查中是可以接受的，但在全量审查中需补足。

**总结**：本轮审查成功拦截了严重的线程安全问题，并提出了防御性编程建议。评分 6/10 较为客观，反映了功能实现虽好但基础规范性（线程安全）存在硬伤。建议开发者重点修复线程模型，并在后续开发中加强对“主线程约束”的认识。
