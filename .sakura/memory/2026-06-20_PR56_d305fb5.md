# 全量重审反思报告

## 1. 审查质量评估

### 覆盖度：严重不足

本次审查**零评论输出**，但根据项目记忆中的强制规则，以下内容理应被覆盖：

| 应触发规则的变更 | 对应规则 | 实际覆盖 |
|---|---|---|
| `ClientAuthLockoutManager` (+120行) | 新增文件 >50 行必须有至少 1 条意见 | ❌ 缺失 |
| `ConnectScreenMixin` (+24行) | Mixin 必须评估兼容性与模组冲突 | ❌ 缺失 |
| `ServerConfig` (+6行配置项) | 配置全生命周期审查（默认值/边界/热更新） | ❌ 缺失 |
| 整体认证模块变更 | 认证模块每次审查需重新评估安全风险 | ❌ 缺失 |

### 准确度与完整性：无法评估

审查引擎内部检测到了 major findings，但评论输出被验证逻辑截断，导致用户侧看到"无评论"。这不是误判问题，而是**输出管线断裂**。

## 2. 核心问题诊断：审查系统内部矛盾

```
检测到 major findings
    → 触发约束: major findings require SCORE <= 6
    → 实际 SCORE: None（未赋值）
    → 验证失败 → 整个输出被丢弃
    → 用户看到: "无评论"
```

**这是一个严重的系统性缺陷**：发现问题但不输出，比不发现问题更危险。用户触发了手动全量重审（说明对之前的审查不满意），结果得到的是比增量审查更差的体验。

## 3. 从变更内容推断应关注的风险点

虽然无法看到代码细节，但基于文件名和变更量，以下风险点几乎必然存在：

### `ClientAuthLockoutManager`（+120行，新增）
- **静态可变状态**：锁定状态大概率使用静态字段存储，根据项目历史，这是高频问题域。必须验证 `volatile`/`AtomicBoolean` + `reset()` + 生命周期清理
- **锁定解除条件**：是否只依赖网络包解锁？断线后锁定状态能否正确重置？
- **线程安全**：锁定状态的读写可能跨越网络回调线程和渲染线程

### `ConnectScreenMixin`（+24行）
- Mixin 注入点是否与其它认证/连接模组（如 AuthMe 重定向端）冲突
- 拦截逻辑是否有 fallback，避免 Mixin 注入失败时玩家完全无法连接

### `AuthLockoutPayload`（+32行，新增）
- 网络包是否包含敏感信息（如锁定原因是否泄露服务器内部状态）
- 包体大小是否合理，是否有不必要的序列化开销

### `ClientPayloadHandler`（+21行）
- 新增的处理分支是否遵守了"网络请求禁止静默丢弃"规则
- 异常路径是否有日志记录

## 4. 规范完善建议

### 新增规则

| 规则 | 说明 |
|------|------|
| **审查输出降级策略** | 当评分验证失败时，必须仍输出已检测到的 findings，附加"评分验证异常"警告，禁止静默丢弃 |
| **锁定状态生命周期** | 新增客户端锁定/封禁类状态时，必须审查：(1) 设置路径 (2) 清除路径（含异常断线） (3) 跨会话持久化决策 |
| **认证拦截链完整性** | Mixin 层面的连接拦截必须有非 Mixin 的 fallback 机制，防止注入失败时功能静默失效 |
| **major findings 强制输出** | 任何 severity >= major 的发现必须写入评论，不受评分约束影响 |

### 修改现有规则

- **"新增文件 >50 行必须有至少 1 条意见"** → 升级为硬约束，违反时审查结果标记为 `invalid` 而非 `comment`
- **"认证模块每次审查需重新评估安全风险"** → 细化为检查清单：传输加密、锁定绕过可能性、状态不一致攻击面

## 5. 经验教训

### 对审查系统
- **输出管线必须有最终兜底**：无论中间验证环节如何失败，已生成的 findings 绝不能丢弃。这类似于日志系统中的 `never drop events` 原则
- **None 评分应视为合法输入**：评分验证逻辑应将 `None` 视为"未评分"而非"评分不合规"，走不同分支处理

### 对审查策略
- **全量重审不应复用增量审查的脆弱管线**：手动全量重审意味着用户对之前结果不信任，应使用更鲁棒的输出路径
- **认证模块是持续攻击面**：每次认证相关变更都是安全审计触发器，不应依赖通用审查流程覆盖

### 值得持续关注
- `ClientAuthLockoutManager` 的静态状态在多次连接/断线场景下的累积效应
- 锁定机制与现有 `PlayerPasswordManager` 静态状态的生命周期是否会产生级联重置问题
- 客户端锁定后，玩家关闭重开游戏是否能正确解除（可能涉及配置持久化决策）

## 6. 给用户的建议

本次全量重审因审查系统内部验证失败未产出有效结果，建议：
1. 重新触发审查（系统偶发性问题）
2. 若反复失败，可尝试将 PR 拆分为更小的提交（认证锁定核心逻辑 vs UI 适配 vs 网络层），降低单次审查复杂度
3. 重点关注上述第3节列出的风险点，这些是基于项目历史模式的高概率问题
