## 2. 失败根因分析

错误信息 `FINDINGS may contain only FINDING blocks` 表明：审查输出在 FINDINGS 段落中混入了非 FINDING 格式的内容（如纯文本、空行、注释等）。这是**输出格式约束**问题，非代码理解问题。

**具体可能的触发场景：**
- 变更涉及新增文件较多（2个新增 + 11个修改），可能触发了某种"无问题"的文本输出而非空 FINDINGS
- 审查策略 `standard` 对空结果的处理路径存在格式漏洞

## 3. 发现的模式（基于变更预判）

### 代码模式
从文件命名和修改范围推断，本次变更遵循项目既有模式：
- **网络同步模式**：`Payload` → `ModNetwork.register` → `ClientPayloadHandler` 三层结构
- **客户端状态机**：`ClientState` 持有状态，`HUDRenderer`/`TitleWorldRenderer` 负责展示，`Mixin` 负责拦截
- **服务端配置驱动**：`ServerConfig` 扩展配置项，`PlayerPasswordManager` 消费配置

### 架构观察
认证锁定机制采用了**服务端判定 + 网络下发 + 客户端执行**的架构，这是正确的安全设计（客户端不可信）。但需关注：客户端锁定状态是否仅作为 UI 提示，服务端是否仍为最终校验方。

## 4. 规范完善建议

### 新增审查规则

| 规则 | 说明 | 优先级 |
|------|------|--------|
| 认证锁定状态可重置 | `ClientAuthLockoutManager` 的锁定状态必须提供显式 reset，且在断开连接时调用 | 阻塞级 |
| 网络包输入验证 | `AuthLockoutPayload` 反序列化时必须验证锁定次数、时长等字段的边界值 | major |
| 锁定策略服务端兜底 | 客户端锁定仅作 UI 限制，服务端必须在包处理层做二次校验 | 阻塞级 |

### 工具层面修复建议
- **空结果处理**：当审查无发现时，FINDINGS 段应输出空或标准占位符，禁止输出任何非 FINDING block 的文本
- **大变更降级策略**：当变更文件超过 10 个时，考虑自动拆分为多次子审查，避免单次输出过长导致格式失控

### 审查流程改进
- **格式校验前置**：在输出结果进入验证环节前，增加本地格式预检
- **失败重试机制**：格式错误时应自动重试一次（清理上下文后），而非直接返回空结果
- **最小有效输出**：即使审查完全通过，也应输出结构化的"通过确认"而非空内容，避免触发格式边界条件
