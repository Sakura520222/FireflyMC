## 2. 发现的模式

**代码模式**
- **静态状态散落**：`ClientState.currentServerIp`、`BuildAnchorManager` 的 `ConcurrentHashMap`、`ModNetwork` 的反射分发器——项目对静态可变状态有路径依赖，但缺乏统一的生命周期管理框架
- **防御编程断层**：服务端→客户端方向的数据校验几乎为零（lockoutMinutes 无范围校验只是冰山一角）

**架构观察**
- **AI 模块正在重构但缺乏顶层设计**：从 `ToolContext` 移除 anchor 字段到 `BuildAnchorManager` 独立管理，方向正确，但 `AgenticToolLoop` 的截断逻辑说明工具调用的数据流未被整体梳理
- **网络层是系统性弱点**：`ModNetwork`（反射空 catch）、`ClientPayloadHandler`（无校验）、`ClientState`（无 volatile）三个文件构成客户端网络层的"缺陷三角"，各自独立修复效率极低

**开发者行为模式**
- **增量逃避策略**：连续 5 轮（含本轮）只提交与历史 major 无关的小改动，利用 quick 模式"增量正确"的特性规避困难修复
- 评分从 5→6 后卡住，说明开发者已触及能力或意愿天花板

## 3. 规范完善建议

### 新增规则

| 规则 | 说明 |
|------|------|
| **API 协议一致性** | 发送给外部 API 的历史数据必须与实际执行状态严格一致，截断/过滤后必须同步更新所有派生数据结构 |

### 修改规则

- **"同类缺陷>2轮未修→阻断"** 应细化为：**"同一文件 ≥3 轮出现 major 且未修复，直接阻断并建议更换负责人"**——当前 `ModNetwork` 已 4+ 轮，规则执行力度不足

## 4. 经验教训

**工具调用截断是新问题类型**
`AgenticToolLoop` 的 `subList` 截断后 `buildToolCallsJson` 数量不匹配，本质是**局部优化破坏全局一致性**。未来审查 AI/LLM 集成代码时，须特别关注：
- 历史消息截断是否同步更新所有派生状态
- 工具调用计数器是否与实际执行对齐
- 截断边界是否可能导致 API 拒绝（OpenAI 要求 tool_calls 与 assistant 消息严格对应）

**quick 模式不应成为"安全区"**
当 PR 积累大量未修复 major 时，quick 模式反而成为开发者逃避修复的工具。应在 PR 级别维护一个"未修复 major 计数器"，超过阈值自动升级审查策略。

**缺陷三角的修复策略**
`ModNetwork` + `ClientPayloadHandler` + `ClientState` 三个文件的缺陷相互关联（网络接收→状态存储→状态读取），单独修复效率低。应建议开发者作为一个"客户端网络层安全加固"任务统一处理，而非逐个文件修补。

## 5. 增量审查反思

**新增提交未解决任何历史问题**
本次 5 个文件的改动全部是"增量正确"的新功能/小修复，与 4 个历史 major 零交集。这验证了"增量逃避策略"的判断。

**未引入新风险，但掩盖了存量风险**
增量变更本身质量良好（BuildAnchorManager 生命周期处理、ToolContext 精简），但 PR 整体健康度因历史问题持续腐烂而停滞在 6 分。quick 模式的正面评价可能给开发者传递错误信号——"只要新代码没问题就能过"。

**覆盖度因增量视角有所下降**
- `AIChatEventHandler` 被改动，但未追踪其与 `AgenticToolLoop` 的调用关系
- `GetNearbyEntitiesFunctionTool` 的改动涉及工具执行，但未检查其返回值是否受截断影响
- **改进**：增量审查中，若改动文件与存在 major 的文件在同一调用链上，应强制做链路扫描

**建议下一步行动**
1. 在 PR 评论中明确列出 4 个 major 的修复优先级和预计工作量
2. 建议 `ModNetwork` 空 catch 问题由资深开发者直接提交修复 PR，而非继续等待原开发者
3. 下一轮审查若 4 个 major 仍未修复，应升级为 block 并建议拆分 PR——将本次增量变更独立合并，历史 major 作为独立跟踪项
