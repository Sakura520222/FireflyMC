## 2. 发现的模式

**代码模式**
- 开发者能处理简单规范问题（硬编码→常量），但面对架构级问题无动于衷
- 修复策略呈现"避重就轻"倾向：先修容易的，跳过困难的

**架构观察**
- 本 PR 核心功能（防暴力破解）存在根本性信任边界设计错误
- 这不是代码质量问题，是**设计阶段缺失**——安全功能上线前应做威胁建模
- 服务端仅下发数值、客户端自主执行锁定的模式，在任何安全审查中都是一票否决项

## 3. 规范完善建议

**建议新增规则：**

| 规则 | 说明 |
|------|------|
| 安全功能架构前置审查 | 涉及认证/限流/锁定的新功能，首轮审查必须包含信任边界分析，缺失则直接 major |
| 历史问题状态追踪 | 每轮审查对未解决问题须标注：未触碰/尝试修复失败/部分修复，禁止纯复制 |
| 修复颗粒度下限 | 单行修复 +N 个 major 未动时，评论须明确要求"下一轮必须包含哪个 major 的修复" |
| 连续微修复降级机制 | 连续 2 轮仅提交 trivial 修复而不触碰 major，评分冻结不再提升 |

## 4. 经验教训

**关键教训：**
- **三轮修复失败的空 catch 问题**：说明开发者可能不理解"反射分发器为什么要记日志"的本质。单纯说"加日志"无效，应给出具体代码模板：`catch (Exception e) { LOG.warn("Payload dispatch failed for {}", payload.getClass().getSimpleName(), e); }`
- **安全架构问题无法增量修补**：纯客户端锁定需要重构为"服务端状态追踪 + 客户端同步展示"，这不是 diff 级别的修复，需要新 PR
- **版本号修复是信任信号**：开发者能正确应用 `VERSION` 常量，说明具备基础规范遵从能力，问题在于复杂场景
