## 3. 规范完善建议

### 建议新增规则：**测试代码线程治理**

| 子规则 | 说明 |
|--------|------|
| 测试 executor 必须 daemon | 测试中创建的线程池必须设 `setDaemon(true)`，防止阻塞 JVM 退出 |
| 测试 await 必须超时 | `CountDownLatch.await()` / `Future.get()` 在测试中禁止无限等待 |
| 超时常量提取 | 同一测试类内多处超时应提取为 `static final` 常量，避免不一致 |

> 现有规范"单线程 executor 禁止 join"和"P2P 超时强制兜底"覆盖了生产代码场景，但测试代码的同等要求未显式声明。测试代码的副作用（线程泄漏、CI 挂起）虽不影响用户，但影响工程效率和 CI 稳定性。

### 建议修改规则：**同类缺陷批量修复** 

补充约束——>quick 模式下，若修复的是模式性缺陷（如"executor 未设 daemon"），审查者应至少 grep 同文件确认无遗漏实例，而非仅验证 diff 范围。

## 4. 经验教训

**超时硬编码的隐患**：本次 5 秒硬编码出现在两处（latch 和 future），当前无问题，但若未来需要调整（如 CI 环境变慢），容易遗漏。提取常量成本极低，应作为习惯性建议提出——即使不阻塞合并，也值得在评论中提及。

**测试代码 ≠ 可以降低标准**：这次改动证明团队对测试质量有意识，但审查者容易因"只是测试"而放松警惕。测试中的线程泄漏和无限挂起对 CI 的杀伤力不亚于生产 bug。

**辅助方法抽取的价值**：`probeExecutor()` 的抽取比直接在两处各自 `setDaemon(true)` 更优——它建立了"测试用 executor 必须经过此工厂"的约定，从结构上防止未来新增测试时遗漏。
