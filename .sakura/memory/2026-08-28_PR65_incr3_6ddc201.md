**三、规范完善建议**  

1. **新增审查规则**  
   - **异常捕获统一化**：所有跨线程/跨模块的异步任务（虚拟线程、CompletableFuture、Executor）必须在最外层捕获 `Throwable` 并记录统一日志（使用项目统一的 `LOGGER.error`），禁止 “空 catch”。  
   - **重试机制审查**：对每个 `try…catch` 中实现的重试（如 `JavaSoundOutput.tryOpen`），必须检查：① 最大重试次数是否受配置化管理；② 重试间隔是否可配置；③ 每次异常均记录日志并累计计数；④ 超过阈值后上报至 `ClientMusicFailReporter`。  
   - **缓存并发可见性**：任何对共享缓存（`MusicCache`、`MusicQueueManager`）的读写必须使用 `volatile` / `AtomicReference` / `synchronized`，并在代码审查中显式标注并发约束。  
   - **后台线程资源限制**：启动虚拟线程前必须评估是否会产生 “无限线程” 风险，建议使用线程池 (`Executors.newVirtualThreadPerTaskExecutor()`) 并在关闭时调用 `shutdown()`。  

2. **项目特有的规范要点**  
   - **PlaybackId 校验**：在所有需要跨线程状态同步的地方（LRC 解析、缓存加载、播放结束回调），必须使用 **双重校验**（队列检查 + `MusicPlaybackState` 对象比对），并在代码注释中标明原因。  
   - **日志脱敏**：`MusicServerBridge.onClientFailure` 中的日志仍未使用 `sanitize()`，应在审查清单中加入 “日志脱敏覆盖率 ≥ 100%”。  
   - **HTTP 重定向安全**：所有 `HttpClient` 实例的 `Redirect` 必须显式设为 `NEVER`，并在重定向后校验最终 URI scheme 为 `https`，防止明文降级。

**四、经验教训**  

| 教训 | 具体表现 | 改进措施 |
|------|----------|----------|
| **“隐蔽异常”易被忽视** | LRC 解析的虚拟线程未捕获异常，导致歌词消失且无日志。 | 在审查时对所有 **异步入口**（虚拟线程、Executor、CompletableFuture）进行 “异常捕获检查”。 |
| **增量审查容易遗漏跨文件影响** | 本轮审查聚焦在 `MusicPlaybackManager`、`MusicCache`，但对 `MusicPlayer.tryOpen` 中的重试逻辑未展开检查。 | 在增量审查后，进行 **“影响范围回溯”**：列出所有直接或间接调用的类/方法，逐一确认没有遗漏的风险点。 |
| **配置化缺失导致硬编码风险** | 重试次数（10）和延迟（100 ms）写死在代码里。 | 将此类阈值抽取到 `mod.toml` 或 `Config` 类，并在审查中检查 **配置可见性**（`volatile`/热更新） |
| **跨平台文件句柄约束** | `deletePartFile` 在 Windows 下必须先关闭流，否则会抛异常。 | 在单元测试中加入 **跨平台文件操作** 场景，确保 `close → delete` 的顺序在所有 OS 上均安全。 |
| **文档‑代码同步** | `MusicCache` 的延迟初始化说明在代码注释里，但未在项目文档中更新。 | 在 PR 模板中强制要求 **“文档更新”** 检查项，审查时对应验证。 |

**总体结论**  
增量审查成功验证了大部分历史问题的闭环，且本轮提交在性能与并发安全上取得显著进展。但由于审查仅聚焦在增量改动，**跨文件的副作用（如重试机制、异常捕获）仍有遗漏**。未来应在增量审查后执行一次 **“影响链路回溯”**，确保所有关联模块均得到检查，并将异常捕获、配置化、日志脱敏等通用规则提升为必检项。这样既能保持增量审查的高效，又能避免因视野局限而产生的潜在缺陷。
