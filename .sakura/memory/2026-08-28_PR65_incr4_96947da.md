**二、发现的模式**

- **代码模式**  
  1. **防御式编程**：在 `MusicCache` 中出现了多层校验（服务端+客户端+路径归一化），体现了“防御深度”理念。  
  2. **幂等写入**：缓存标记写入失败仅导致下次扫描，保持幂等性，符合容错设计。  
  3. **虚拟线程 + 同步块**：播放 worker 迁移到虚拟线程后仍保留了 `synchronized` 路径（`SourceDataLine.write`、缓存初始化），暴露了 JDK 21‑24 虚拟线程的 “pinning” 限制。  
  4. **硬编码阈值**：`logSlow` 中出现硬编码 `2_000L` 与常量 `SLOW_LOG_THRESHOLD_US` 不统一，说明阈值管理仍不够集中。  

- **架构观察**  
  1. **单向依赖链**：`MusicPlaybackManager → ClientMusicFailReporter → MusicPlaybackFailedPayload`，层级清晰，职责分离明确。  
  2. **缓存层与播放层耦合**：`MusicCache` 的路径解析直接被 `MusicPlayer`、`MusicPlaybackManager` 调用，若后期需要替换缓存实现，耦合度仍然较高。  
  3. **测试驱动**：大多数核心改动都有对应单元测试（`StallGuardInputStreamTest`、`MusicCacheTest`），但仍有安全类改动缺失测试，表明测试覆盖率的盲区主要集中在 **防御性路径** 上。

**四、经验教训**

1. **防御深度必须配套测试**  
   - 第三层防御（路径归一化）虽在代码中实现，但若未通过单元测试验证，仍可能因实现细节（如 `Path.normalize()` 行为差异）产生漏洞。  
2. **增量审查易产生“盲区”**  
   - 只看增量改动时容易忽视 **已有模块的旧缺陷**（如 LRC 解析异常、硬编码阈值），建议在每轮增量审查后进行一次 **模块全局检查**（尤其是涉及同一资源的文件）。  
3. **虚拟线程迁移需同步审查平台线程特性**  
   - 虚拟线程的 “pinning” 行为在不同 JDK 版本表现不同，审查者应在代码评审时标注 JDK 兼容性要求，或在 CI 中加入 **JDK 24+** 的兼容性测试。  
4. **日志脱敏与统一**  
   - 本次审查提到的 `logSlow` 硬编码阈值，说明日志相关的阈值、脱敏、统一入口仍有散点。建议在审查清单里加入 **“所有日志使用统一日志工具（logSafe / logError）”** 检查项。  
5. **异常路径的覆盖率**  
   - `StallGuardInputStream` 已加入单测覆盖异常路径，但仍有 **网络请求、文件 I/O** 等异常分支未覆盖。后续审查应关注 **异常路径的单元测试覆盖率 ≥ 90%**。
