#### 2. 发现的模式
**代码模式**：开发者倾向“修复而非重构”，例如删除 `isVerified()` 但保留类似逻辑的 `isPendingVerification()`，体现了渐进式改进习惯。常量提取（如 `AUTH_SUCCESS_SIGNAL`）显示对魔数的敏感度提升。

**架构观察**：项目模块化清晰（auth、kit、network 分离），但认证模块仍存在**上帝类倾向**（如 `PlayerPasswordManager` 集中处理密码校验、哈希、会话管理）。客户端与服务端校验双层防御（如密码长度）是良好实践。

#### 3. 规范完善建议
**新增规则**：
- **增量修复必须扫描同模块历史问题**：本次 PR 修复了密码验证，但未检查 `PlayerPasswordManager` 中其他弱哈希或密码策略问题。建议审查模板强制要求“是否波及同模块已知风险”。
- **空方法/注释清理标准**：明确“删除功能后必须清理相关残余代码”，避免空注释或冗余方法。

**项目特有规范**：
- **密码策略统一审查**：鉴于历史多次出现密码安全问题，建立专项检查项：哈希算法（推荐慢哈希）、密码复杂度（禁用纯数字）、传输加密（避免明文）。
- **静态状态生命周期管理**：`PlayerPasswordManager` 中的静态字段（如 `PASSWORD_VERIFIED_PLAYERS`）需明确重置时机，防止测试或重启残留。

#### 4. 经验教训
**未来审查要点**：
- **高频路径性能**：虽然本次未涉及，但 `PlayerPasswordManager` 的哈希计算在并发场景可能成为瓶颈，需评估正则/哈希性能。
- **线程安全默认悲观**：`StarterKitManager` 的 `synchronized` 修复是积极案例，未来所有静态方法需假设多线程访问。

**技术模式反思**：
- **SHA-256 的适用性**：在 Minecraft mod 离线防顶号场景中，SHA-256 + salt 可能足够，但应记录为“临时方案”，未来升级至 bcrypt/argon2。
- **UI 与服务端校验一致性**：客户端 `EditBox.setMaxLength(32)` 与服务端 `password.length() > 32` 的双层防御是优秀实践，可推广至其他输入校验。
