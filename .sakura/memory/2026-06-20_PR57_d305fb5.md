# 审查反思报告 — PR #57

## 1. 审查质量评估

### 覆盖度：有结构性盲区

链路驱动审查（配置→触发→传输→处理→展示）有效覆盖了功能完整性，但**链路内部的新增文件实现细节被弱化**：

- **ClientAuthLockoutManager（120行新增）**：作为"处理"环节核心，其文件IO实现未深入审查——缺少对并发写入竞争（多线程同时触发lockout）、JSON文件损坏恢复、目录存在性检查的审视
- **ConnectScreenMixin**：项目记忆明确要求 Mixin 审查须验证"注入点兼容性 + 多mapping环境"，本次未提及
- **lockoutMinutes=0 的语义**：配置范围 0-1440，0 发送到客户端后 `ClientAuthLockoutManager.recordLockout` 如何处理？是否产生立即过期的废记录？未验证边界值的端到端行为
- **服务端无状态导致的重复触发**：`PlayerPasswordManager` 只发包不记录锁定状态，锁定期内玩家换IP重连，服务端是否会反复执行"验证失败→发包→断开"的无用循环？

### 准确度：无误判，但竞态严重程度可商榷

4个 major + 2个 minor 标记均合理，与项目规范高度吻合。值得讨论的是**竞态条件是否应升级为 blocker**：如果 `AuthLockoutPayload` 经常丢失（TCP 不保证应用层包序在 disconnect 前到达），整个功能链路在"触发→传输"环节就断裂了，后续所有环节形同虚设。这是功能根本性缺陷，而非实现质量问题。

### 完整性：PR 描述与实现的矛盾未作为独立发现

PR 描述明确写"防暴力破解"，审查总结正确识别出实际设计目标是"减少客户端反复连接对服务器的骚扰"，但未将**PR 描述与实现的不一致**作为独立发现提出。这种不一致往往是开发者对需求理解偏差的信号，应作为第一个审查点显式标注。

## 2. 发现的模式

### 代码模式
- **ModNetwork 空 catch 是系统性复制问题**：非偶发，而是新增 handler 时直接复制已有模板的结果。"三轮修复仍失败"说明**代码生成/模板层面**有缺陷，而非逐处修复能解决
- **ClientState 静态状态持续膨胀**：🔴 模块中又新增 `currentServerIp`，无 volatile、无 reset、无生命周期管理，恶化趋势未因历史审查而停止
- **安全功能客户端化倾向**：密码验证是服务端的，但锁定机制推给客户端，反映开发者对安全边界缺乏系统性认知

### 架构观察
- **服务端-客户端职责划分混乱**：安全控制端到端应在服务端，项目倾向于把状态管理外推到客户端
- **ModNetwork 反射分发器已构成技术债务放大器**：每新增一个 handler，就复制一次空 catch 反模式，债务线性增长
- **文件 JSON 作为客户端持久化**：在游戏 mod 场景下脆弱（写权限、多实例冲突、损坏无恢复），但项目已形成路径依赖

## 3. 规范完善建议

### 新增规则

| 规则 | 说明 |
|------|------|
| **"发送后断开"竞态禁止** | 网络发包后立即 disconnect() 的，必须使用回调确认发送完成或带序号机制。泛化为"网络操作+连接操作的组合原子性" |
| **安全功能端到端验证** | 声称"防X"的功能必须验证攻击面在服务端全覆盖。纯客户端安全控制必须标注为"体验优化"而非"安全防护"，PR 描述不得使用安全术语 |
| **新增文件最低审查清单** | >50行新增文件必须独立审查：异常处理策略、线程安全、资源清理、边界条件。链路审查不替代文件级深度审查 |
| **JSON 文件持久化审查** | 新增文件 IO 须检查：并发写入保护、文件损坏恢复、目录存在性、IO 异常不静默 |
| **🔴 模块增量提升审查强度** | 在已标记🔴的模块中新增代码，自动将相关发现的严重程度提升一级 |

### 修改规则

- **"网络包客户端防御校验"**：补充"校验范围必须与发送端配置范围一致或更严格"，强调范围对称性
- **"Mixin 兼容性验证"**：从"新增/移除时评估"改为"所有涉及 Mixin 的 PR 均须逐个验证"，因为本次遗漏了 ConnectScreenMixin 的注入点分析

## 4. 经验教训

### 核心教训

1. **链路审查 + 文件深度审查须双轨执行**：链路法保证功能完整性，但新增文件的实现质量需要独立的文件级审查。本次 ClientAuthLockoutManager 120 行几乎"穿透"了链路审查

2. **PR 描述与代码的语义对齐是第一优先级**：当描述说"防暴力破解"而实现是纯客户端锁定时，应在审查总结首行就指出这个矛盾，而非 buried 在架构建议中

3. **"三轮修复失败"的模块应触发开发冻结**：ModNetwork 的空 catch 问题经过三轮未能解决，说明当前开发者在处理该模块时存在系统性认知缺陷。正确的动作是**拒绝在该模块上继续增量开发**，要求先重构基础设施或由资深开发者介入，而非继续指出问题等待第四轮修复

4. **配置边界值须端到端走查**：审查了 `lockoutMinutes` 的配置范围（0-1440）和客户端缺少校验，但没有把"0"作为测试用例走完整条链路。边界值审查不能止于声明侧

5. **安全功能的审查应从攻击者视角倒推**：如果从"攻击者想绕过锁定"的角度倒推，会立即发现"删文件即可绕过"这个问题，而不需要先读完整个实现再判断。安全类 PR 应**先做威胁模型，再做代码审查**
