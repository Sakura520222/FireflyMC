# 代码审查深度反思

## 1. 审查质量评估

### 覆盖度：中等，存在盲区

**已覆盖的点**：时间单位一致性、PR描述与实现一致性、线程安全委托、资源清理、边界条件

**遗漏的问题**：
- **竞态条件风险**：`warningTask` 的初始化与 `stop()` 之间缺乏同步机制，若在 `start()` 执行中途调用 `stop()`，可能出现任务泄露
- **配置热更新场景**：每次 `sendWarning()` 从配置读取值，但如果 `warningSeconds` 在运行时被修改，不会重新调度任务，行为会变得不一致
- **消息显示逻辑缺陷**：审查指出"显示固定值而非实际倒计时"，但未深究这实际上是**功能性 bug**——用户看到"60秒后清理"，但可能实际只剩10秒

### 准确度：基本合理

- 时间单位混用标记为 🟡 建议 → ✅ 正确，不影响功能
- PR描述不一致标记为 💡 优化 → ⚠️ 偏轻，这可能是需求实现不完整，而不仅是描述问题

### 完整性：有待提升

审查接受了"当前单次提醒作为 MVP 合理"的说法，但 PR 描述明确提到"10s、5s、3s分别提醒"，这暗示作者**原意是多阶段提醒**。审查未追问这是否为实现缺陷。

## 2. 发现的模式

### 代码模式
```
定时任务模式：ScheduledExecutorService + scheduleAtFixedRate
线程委托模式：异步线程 → server.execute() → 主线程执行
资源清理模式：cancel() + 置 null + 日志记录
配置开关模式：0 = 禁用，>0 = 启用并作为参数值
```

### 架构观察
- Manager 单例负责任务生命周期管理
- 配置与逻辑分离，但缺少配置变更的响应机制

## 3. 规范完善建议

### 新增审查规则

| 规则 | 说明 |
|------|------|
| **PR描述-实现对照** | 描述中列举的功能点必须逐一在代码中找到对应实现 |
| **时间单位一致性** | 同一方法/功能块内的 `TimeUnit` 必须统一，否则需注释说明 |
| **动态显示值校验** | 向用户展示的数值必须是计算后的实际值，禁止直接展示配置原始值 |
| **定时任务线程安全** | `start()`/`stop()` 必须考虑重入和并发调用场景 |

### 项目特有规范
- Bukkit 消息发送必须走 `server.execute()`
- 配置项范围校验应在加载时完成并记录 warn

## 4. 经验教训

### 值得关注的要点

1. **"描述 vs 实现"分歧时优先质疑实现**：当 PR 描述更具体（10s/5s/3s）而实现更简单（单次60s）时，大概率是实现遗漏，而非描述夸大

2. **配置值≠显示值**：涉及用户展示的数值，必须追踪其来源是"配置原始值"还是"计算后的实际值"

3. **定时任务的隐含耦合**：`warningTask` 和 `cleanupTask` 的周期必须保持特定关系（warningDelay = intervalSeconds - warningSeconds），这种隐含约束应在代码注释中明确

### 对快速审查策略的反思

本次使用 `quick` 策略，导致：
- 跳过了对并发安全性的深入检查
- 对"显示值 bug"的严重性判断偏轻
- 未追踪配置值到用户界面的完整链路

**建议**：即使快速审查，对于涉及"用户可见输出"的变更，应至少完整走读数据流。
