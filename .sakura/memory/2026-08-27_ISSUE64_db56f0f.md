**6. 经验教训 & 建议**  

| 经验点 | 说明 |
|--------|------|
| **异常统一上报** | 客户端在 `StallGuardInputStream` 触发时直接上报 `STREAM_INTERRUPTED`，缺少 **分级**（可恢复 vs 不可恢复）。后续所有流异常应分为 “暂时不可用” 与 “致命错误”，并在上报前做 **重试策略**。 |
| **Quorum 判定细化** | 业务上把 “一次本地失败” 与 “多数客户端同时失败” 用同一条路径处理，导致误判。建议在 `MusicQueueManager.shouldFailEarly` 中引入 **状态位**（`hasStartedPlayback`），仅在已进入播放状态后才采用 **容错重试**。 |
| **断点续传实现** | 目前仅在打开流阶段做了 3 次重试，播放中未实现续传。以后涉及 **大文件流式播放**（音乐、视频、资源包）时，统一采用 **Range‑request + 本地缓存** 的通用实现。 |
| **日志脱敏与可追溯** | 对于 “无法播放，已自动跳过” 的触发路径，需要在 **服务器** 与 **客户端** 记录 **songId、playerId、offset、异常类型**，方便后续定位是网络抖动还是 CDN 响应异常。 |
| **单元/集成测试覆盖** | `MusicQueueManager` 已有 JUnit 用例，但缺失 **网络抖动模拟** 与 **多客户端 quorum** 场景。建议新增 **MockHttpServer** + **多线程模拟** 的集成测试，确保改动不产生新回退。 |
| **配置化阈值** | `StallGuardInputStream` 的 30 s 阈值硬编码，建议搬到配置文件（`music.stallGuardTimeoutMs`），并在 UI 中提供 **调试开关**，便于快速定位不同网络环境下的最佳值。 |
| **跨模块影响评估** | 音乐播放链路与 **玩家状态同步**、**服务器广播** 紧密相连。任何改动都应在 **全局影响评审** 中检查是否会导致 **状态错位**（如进度条回到 0 导致 UI 误判）。 |

**结论**：整体分析思路清晰，定位准确，提出的修复方向可行。后续在实际实现时，需要重点关注 **流续传的并发安全**、**quorum 判定的细化** 与 **完整的自动化测试**，并在标签、标题以及优先级上做细微校正，以提升 Issue 管理的效率与可追溯性。
