## 2. 发现的模式  

### 2.1 代码模式  

| 观察 | 具体表现 | 潜在影响 |
|------|----------|----------|
| **统一的 `Redirect.ALWAYS`** | `MusicPlayer`、`MusicApiClient` 均使用 `HttpClient.Redirect.ALWAYS`，且未在统一封装层做 scheme 校验。 | 形成跨模块的安全弱点，错误修复需在多处同步修改。 |
| **同步阻塞在异步链路** | `probeDurationMs(...).join()` 在业务线程中阻塞，且缺少 `orTimeout`。 | 线程池（尤其是虚拟线程）被异常卡死，导致资源泄漏与状态残留。 |
| **日志/异常处理不统一** | 部分网络异常仅记录 `warn`，未上报具体错误码；在 `MusicQueueManager` 中对异常的 `failRequest` 调用缺失。 | 难以定位线上错误，且违反 “网络请求禁止静默丢弃”。 |
| **临时对象创建** | `HttpClient.newBuilder()` 在每次下载/探测时重新创建。 | 频繁的 socket/SSL 初始化可能导致性能波动与资源泄漏。 |
| **状态字段跨线程访问** | `pending`、`sessionId` 等字段在多个线程间直接读写，未使用 `volatile` 或 `Atomic*` 包装。 | 竞态条件风险，尤其在异常路径下更易出现不一致。 |
| **单元测试覆盖度提升** | 新增 `Mp3DurationProbeTest` 与 `MusicQueueManagerTest`，但仍缺少对 **重定向策略** 与 **异常清理** 的测试。 | 测试盲区导致回归缺失。 |

### 2.2 架构观察  

* **客户端‑服务器职责分离**：`MusicServerBridge` 负责把服务器端的 `MusicQueueManager` 状态广播给客户端；客户端的 `MusicPlayer` 负责本地解码与播放。该分层清晰，但 **异常路径**（如下载失败、时长探测异常）在两个层面都有重复的清理逻辑，缺少统一的错误处理抽象层。  
* **网络层依赖链**：`MusicApiClient` → `HttpClient` → `MusicPlayer` → `JavaSoundOutput`。如果在链路中任意一环出现异常，后续层仍可能继续执行（例如 `MusicPlayer` 已经拿到错误的 URL 仍尝试解码），导致资源浪费。  
* **模块耦合度**：`MusicQueueManager` 直接引用 `MusicPlaybackFailedPayload`、`MusicStartPayload` 等网络 payload，说明业务层与网络层耦合较紧。若后续更改协议，需要同步修改业务层代码，增加维护成本。

## 3. 规范完善建议  

### 3.1 新增/修改审查规则  

| 规则 | 适用范围 | 说明 |
|------|----------|------|
| **HTTPS → HTTP 重定向禁止** | 所有 `HttpClient` 使用场景 | 必须显式设置 `Redirect.NEVER`，或在最终 URI 校验 `scheme == "https"`，否则标记 **major**。 |
| **所有 `CompletableFuture.join()` 必须配套 `orTimeout`** | 线程/异步任务实现 | 若缺失超时或统一异常捕获，直接报 **major**。 |
| **网络请求统一错误日志** | `*ApiClient`、`*Network` 包 | 捕获异常后必须记录 **错误码、URL、异常类型**，禁止空 `catch`。 |
| **HttpClient 实例复用** | 项目全局 | 禁止在业务方法内部 `newBuilder()`，应提供单例或池化实例；若必须创建，需在 `finally` 中关闭。 |
| **跨线程共享状态必须使用原子/volatile** | 所有 `static`、`instance` 可被多线程访问的字段 | 未使用显式同步的字段直接报 **major**。 |
| **异常清理统一入口** | `MusicQueueManager`、`MusicPlayer`、`MusicApiClient` | 引入统一的 `handleFailure(Player, Session, Throwable)` 方法，确保 `failRequest` 与状态回滚必然执行。 |
| **安全/可靠性改动必须配套单元测试** | 新增/修改的安全相关代码 | 必须提供至少一种成功路径与一种失败路径的测试（如重定向被拒绝、超时清理）。 |
| **许可证文件与 NOTICE 同步检查** | `licenses/` 目录 | 新增第三方库必须在 `NOTICE.md` 中列明，并在构建产物中加入对应 license。 |

### 3.2 项目特有的规范要点  

1. **点歌系统业务规则统一校验**：在 `MusicQueueManager` 中加入 **业务规则检查**（普通玩家最大 3 首、特权玩家无限、全服上限 50 首）的方法，所有入口必须调用。审查时验证该检查是否被绕过或硬编码。  
2. **HUD 渲染线程安全**：`MusicHudRenderer` 中的 UI 数据（如进度条）若在非主线程写入，需要使用 `MinecraftClient.execute()` 包装，防止渲染线程竞争。  
3. **音频缓存文件路径校验**：缓存写入前必须校验路径是否在允许的根目录下，防止路径遍历。  
4. **JLayer 使用限制**：因为 JLayer 为 LGPL，需要在 `NOTICE.md` 中明确说明使用范围，并在代码注释中标记 `@Licensed("LGPL-2.1")`，审查时检查是否漏掉。

## 4. 经验教训  

| 教训 | 具体表现 | 审查对策 |
|------|----------|----------|
| **安全缺口往往在默认配置里** | `Redirect.ALWAYS` 是 Java HttpClient 的默认选项，导致 HTTPS → HTTP 降级被忽视。 | 在审查 checklist 中加入 “默认网络安全配置检查”。 |
| **异常路径同样需要代码覆盖** | `join()` 异常导致 pending 状态不清理，未被单元测试覆盖。 | 强制要求 **异常路径单元测试**（使用 `CompletableFuture.failedFuture`），并在审查时检查测试覆盖率报告。 |
| **增量审查不等于全局审查** | 本次 PR 只改动了部分类，却未检查 **全局共享的 HttpClient 构造**（在其他模块仍然使用 `ALWAYS`）。 | 对涉及全局资源的改动执行 **全局影响扫描**（如搜索 `Redirect.ALWAYS`），即使不在改动文件中也要标记。 |
| **状态清理必须“一站式”** | `MusicQueueManager`、`MusicPlayer`、`MusicApiClient` 各自有自己的异常处理，导致遗漏。 | 推行 **统一错误处理框架**（如 `FailureHandler.handle(player, session, throwable)`），审查时检查是否使用统一入口。 |
| **许可证合规是持续任务** | 本次新增 JLayer 许可证，但 `NOTICE.md` 的改动仅是 +5 行，容易遗漏。 | 建立 **许可证同步检查脚本**，在 CI 中验证每个第三方 jar 是否对应 LICENSE/NOTICE 条目。 |

### 最后建议  

1. **立即修复**：在 `MusicApiClient` 与 `MusicPlayer` 中将 `Redirect.ALWAYS` 改为 `Redirect.NEVER`，并在获取最终 URI 后强制校验 `https`。  
2. **统一异常清理**：抽象出 `MusicRequestFailureHandler.handle(Player, Session, Throwable)`，在所有异步 `join()`/`get()` 前后使用。  
3. **加入超时**：对所有 `CompletableFuture` 调用添加 `orTimeout(10, TimeUnit.SECONDS)`（或业务合适的值），并在 `exceptionally` 中调用统一清理。  
4. **审查流程改进**：在增量审查前执行一次 **全局安全关键字扫描**（`Redirect.ALWAYS`、`join()`、`catch (Exception)`），并在审查报告中标记所有出现位置。  
5. **测试覆盖**：补全对异常路径的单元测试，尤其是重定向被拒绝、时长探测超时、网络异常导致的 pending 清理。  

通过上述措施，可在下一轮审查中将评分提升至 **6–7 分**，并显著降低生产环境的安全与可靠性风险。祝后续修复顺利！
