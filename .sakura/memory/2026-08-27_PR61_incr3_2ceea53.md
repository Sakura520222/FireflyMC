## 2. 发现的模式  

### 代码模式  

| 模式 | 频率 | 优点 | 潜在风险 |
|------|------|------|----------|
| **事件驱动 + ScreenEvent 注入** | 多次出现（`MusicClientEvents`、`MusicSoundOptionsEvents`） | 解耦 UI 与业务，避免 Mixin 带来的兼容性问题。 | 事件注册位置分散，若未统一管理，可能出现重复注册或忘记注销导致内存泄漏。 |
| **配置集中化 (`Config.java`)** | 所有新功能均通过配置项开启/调节 | 便于玩家自定义，统一管理默认值。 | 配置字段未加 `volatile`，在多线程读取时可能出现可见性问题。 |
| **渲染器内部自行管理 PoseStack** | `MusicHudRenderer` 中大量 `push/pop` | 保证渲染层级安全。 | 缺少 `try/finally` 包裹，若异常提前返回会导致 `pop` 未执行。 |
| **单元测试覆盖业务路径** | `MusicHudRendererTest`、历史 `MusicQueueManagerTest` | 提升回归安全。 | 测试仅在 JUnit 环境运行，未在实际渲染线程中执行，可能遗漏 UI 线程特有的并发问题。 |

### 架构观察  

1. **客户端‑服务器职责明确**：服务器只负责队列与权限，音频解码、渲染全部在客户端完成，避免了跨端同步复杂度。  
2. **模块化依赖图呈星形**：`FireflyMCMod` 为根节点，几乎所有客户端渲染、网络、音乐相关类均直接或间接依赖它，导致 **单点故障**（如 `ModNetwork` 初始化异常会影响整个音频系统）。  
3. **渲染与业务耦合度高**：`MusicHudRenderer` 同时负责 UI、动画、音量同步，职责略显混合，后期若要复用跑马灯或音量控制，拆分会更易维护。

## 3. 规范完善建议  

### 新增/修改审查规则  

| 规则 | 建议内容 |
|------|----------|
| **渲染器状态恢复** | 检查每个 `RenderSystem`、`PoseStack` 的 `push` 必须在同一方法体内配对 `pop`，且使用 `try/finally` 包裹。缺失时标记 **minor**。 |
| **配置可见性** | 所有在多线程读取的 `Config` 字段必须标记 `volatile` 或提供同步读取方法。缺失 → **major**。 |
| **事件注册统一管理** | 引入 `EventRegistry`，要求新增 `ScreenEvent`、`ClientTickEvent` 等必须在 `ModEventBusSubscriber` 中统一注册并在 `onShutdown` 中注销。未遵守 → **minor**。 |
| **热更新验证** | 对每个新增配置项，审查其是否在运行时可通过 UI 或指令热更新，并检查对应的回调是否实现。未实现 → **info**（提醒补全）。 |
| **文件层级安全审计** | 对涉及文件 I/O（如 音频缓存、配置写入）必须检查路径合法性、异常捕获与日志脱敏。缺失 → **major**。 |
| **渲染线程安全** | 所有 UI 相关的 `StringBuilder`、`List` 等在渲染回调中使用前必须声明为 `final` 或在 `synchronized` 块中访问。未检查 → **minor**。 |

### 项目特有规范要点  

1. **音量控制统一入口**：所有音量相关的数值必须经 `MusicVolumeOption` 的 `getValue()`/`setValue()`，禁止直接访问 `Config` 中的原始字段。  
2. **跑马灯动画时间基准**：必须使用 `Minecraft.getInstance().level.getGameTime()` 而非系统时间，以保持服务器/客户端时间同步。  
3. **单元测试覆盖 UI 动画**：新增 `HudAnimationTest`，使用 `RenderSystem` 的 mock 环境验证 `offset` 计算逻辑。

## 4. 经验教训  

| 教训 | 具体表现 | 对策 |
|------|----------|------|
| **增量审查易遗漏全局安全** | 本次审查未再次检查音频下载 URL 白名单，历史问题可能被重新引入。 | 在增量审查前执行 **全局安全检查清单**（如 URL、文件路径），即使文件未改动也要复核。 |
| **渲染异常隐蔽** | `push/pop` 不配对在异常路径下不会触发警报。 | 引入 **渲染器静态分析插件**，自动检测 `push`/`pop` 匹配情况。 |
| **配置可见性忽视** | 多线程读取配置导致潜在的可见性 bug。 | 在代码审查 checklist 中加入 “跨线程读取的配置字段是否 `volatile`”。 |
| **事件注册散落** | 多处散布 `ScreenEvent` 注册，后期难以追踪。 | 实施 **事件中心化** 规范，所有注册写在同一类并加注 `@SubscribeEvent`。 |
| **单元测试覆盖不足** | UI 动画仅在代码层面验证，未在真实渲染线程运行。 | 引入 **集成渲染测试**（使用 `HeadlessMinecraft`），确保 UI 代码在实际渲染循环中不抛异常。 |

## 5. 增量审查反思  

| 维度 | 观察 | 结论 |
|------|------|------|
| **问题是否解决** | - `MusicSoundOptionsEvents` 解决了原先通过 Mixin 注入音量的稳定性问题。<br>- `MusicHudRendererTest` 覆盖了跑马灯偏移计算，验证了之前的动画卡顿。 | 增量提交基本消除了历史审查中列出的 **安全/稳定** 问题。 |
| **新风险** | - 新增的 `MusicVolumeOption` 直接在 UI 线程写 `Config`，未加同步，产生潜在竞争。<br>- `MusicHudRenderer` 中对 `String` 拼接未使用 `StringBuilder`，在长歌词下可能产生 GC 抖动。 | 需要在后续审查中关注 **线程安全** 与 **性能**（GC）两点。 |
| **覆盖度下降** | 只审查了改动文件，未对 `MusicPlayer`（下载/解码核心）重新检查，导致 **文件热点** 仍可能残留未发现的缺陷。 | 增量审查应配合 **热点文件复审**，即对历史风险点进行一次快速回顾。 |

**改进建议**：在增量审查结束后，自动生成 “受影响模块热度报告”，提醒审查者对 **高风险旧文件** 再次执行简要检查（如安全、并发、性能）。这样既保持增量效率，又防止历史缺陷沉淀。

本次审查整体执行得当，成功捕获并解决了之前的安全与稳定性缺陷，且对新功能的业务意图有清晰把握。通过本次反思可以看到，增量审查仍需在 **全局安全、并发可见性、渲染资源管理** 三个维度上加强检查，并通过规范化的检查清单和自动化工具提升覆盖度。后续在这些方向上完善审查流程，将进一步提升代码质量与项目可维护性。
