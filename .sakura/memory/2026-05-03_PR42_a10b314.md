## 深度反思报告：PR #42 审查质量分析

### 一、审查质量评估

#### ✅ 覆盖度：优秀
**已覆盖的问题：**
- 线程安全漏洞（WebSocket executor 阻塞、StringBuilder/Buffer 未同步）
- 架构设计缺陷（上帝类 RelayLobbyMessage、UI 代码重复）
- 资源泄漏风险（Thread 重复 start、pendingBeforeRegister 堆积）
- 配置值与硬编码冲突（SendWindow 未使用配置）
- 断线重连缺失
- 日志安全（token 泄露警告）

**遗漏的问题：**
1. **Netty 事件循环线程阻塞风险**  
   `RelayLobbyWebSocketClient` 使用 Java 11 标准 `HttpClient`，其 WebSocket 回调可能在内部线程中执行，但 `onText`/`onBinary` 中直接调用 `executor.execute()` 处理的逻辑如果耗时过长，仍可能阻塞 HttpClient 的共享线程池。
   
2. **`RelayGuestProxy` 缺少连接数限制**  
   虽然警告了 Host 端缺少速率限制，但 Guest 端 `RelayGuestProxy` 接收来自中继的数据转发时，没有检查本地是否已存在连接，可能多次启动 proxy 导致端口冲突。

3. **P2P 握手超时无兜底**  
   `probeAndPunch` 中没有总超时控制，如果两端 NAT 类型不兼容（如对称型 NAT），握手可能永远卡在 `await()` 状态。

#### 🎯 准确度：良好，但有轻微过判
- **major 调整为 minor**：`SendWindow` 的配置未使用问题，当前实现中 MAX_WINDOW 虽硬编码但窗口清理逻辑存在（`MAX_WINDOW * 4`），不会立即导致内存溢出，可降为 **minor**。
- **major 合理**：WebSocket executor 阻塞问题确实会导致心跳失效，属于核心功能缺陷，级别准确。
- **suggestion 级别合理**：字符串包含匹配 UDP 包、HttpClient 复用等均为优化需求。

#### 📖 完整性：基本理解意图，但缺上下文
审查者正确识别了“公开大厅 + P2P 打洞”的核心功能，但：
- 未追问为何选择 Java 11 HttpClient 而非 Netty（可能因 NeoForge 环境限制）
- 未分析 P2P 打洞失败时的降级路径（代码中只有 `RELAY_HOST_FALLBACK` 但未触发）
- 未评估 Minecraft 1.21.1 中 `SharedConstants` 是否可用（可能需平台适配）

### 二、发现的模式

#### 代码模式
1. **“单线程 executor + 同步等待”反模式**  
   多处使用 `Executors.newSingleThreadExecutor()` 但内部调用 `future.join()`，实际退化为同步执行，失去异步优势。
   
2. **静态状态膨胀**  
   `RelayGuestJoiner` 类中 4 个静态字段管理全局状态，缺乏清晰的生命周期管理（何时重置？）

3. **手写协议解析**  
   UDP 控制包使用 `String.contains()` 解析 JSON，虽然简单但脆弱；`UdpPacketCodec` 中同样手写 JSON，未复用 Gson。

4. **UI 代码复制粘贴**  
   两个 Screen 类 80% 代码相同，表明缺乏可复用的 UI 工具层。

#### 架构观察
- **分层混乱**：`RelayLobbyWebSocketClient` 同时承担连接管理、消息编解码、心跳维护，违反单一职责。
- **强耦合配置**：多处直接读取 `Config` 静态字段，难以单元测试。
- **无抽象的中继协议**：`RelayControlMessage` 与 `RelayLobbyMessage` 存在概念重叠，Guest/Host 消息类型未分离。

### 三、规范完善建议

#### 新增审查规则

| 规则 ID | 规则名称 | 说明 |
|---------|----------|------|
| **THD-05** | 单线程 executor 禁止内部 join | `SingleThreadExecutor` 中调用 `Future.join()` 会导致线程阻塞，应改为异步回调 |
| **CON-11** | StringBuilder/ByteBuffer 在回调中需同步 | WebSocket/HTTP 回调可能被不同线程调用，累加器必须线程安全 |
| **ARC-08** | 静态可变状态需明确生命周期 | 多个静态字段跨线程访问时，必须提供 reset 方法或使用 volatile |
| **PERF-07** | HttpClient 实例应复用 | 每次 `ensureConnected` 创建新 HttpClient 会产生大量临时对象 |
| **SEC-06** | 日志中禁止输出 token/secret | 审查所有 `logger.debug/info` 调用，确保敏感字段被脱敏 |

#### 项目特有规范
- **Minecraft 版本抽象**：硬编码版本号 `1.21.1` 需改为从 `SharedConstants` 或 Mod 元数据读取。
- **P2P 超时兜底**：所有 `CompletableFuture.join()` 必须配套 `orTimeout()`（Java 9+）或 `get(timeout, unit)`。
- **UI 工具类强制抽取**：超过 10 行的绘制代码出现在第二个 Screen 时即应抽象。

### 四、经验教训

#### 未来审查关注点
1. **executor 内部阻塞审查**：见到 `executor.submit(() -> { ... future.join() ... })` 立即标记为 major。
2. **WebSocket/HTTP 回调线程模型**：默认假设回调来自未知线程，所有共享状态需同步。
3. **配置值传递路径**：跟踪配置项从 `Config` 到实际使用位置的完整路径，验证是否被忽略。
4. **重连机制必检**：任何网络长连接（WebSocket、TCP）必须有断线重连，缺失则 major。

#### 对 P2P/中继类 PR 的专项经验
- **打洞成功率非功能需求**：审查时需确认是否有降级到中继转发的 fallback，否则对称 NAT 用户完全无法使用。
- **UDP 包乱序/丢包容忍**：现有 `ReorderBuffer` 和 `SendWindow` 基础框架正确，但需关注窗口满时的背压（应暂停发送而非无限缓冲）。
- **房间生命周期**：Host 退出时是否正确通知中继服务端清理房间？需检查 `onClose` 或 `ShutdownHook`。

#### 量化建议
- 建议团队引入 **Error Prone** 或 **SpotBugs** 自动检测 `join()` 在 executor 内的调用。
- 为 P2P 模块补充单元测试，至少覆盖：`ReorderBuffer` 乱序重组、`SendWindow` ACK 重传、`UdpPacketCodec` 编解码。

### 总结

本次审查质量**较高**（8.5/10），覆盖全面且级别基本准确，仅个别误判。最大亮点是指出了**executor 内阻塞**这一隐蔽但致命的设计缺陷。改进方向在于：
1. 加强对异步代码中同步等待的敏感度
2. 要求提供 P2P 握手超时和降级策略
3. 强制抽象重复的 UI 代码

PR 作者应优先修复线程安全和断线重连问题后再合并，否则生产环境可能出现“心跳停止但表面正常”的静默故障。
