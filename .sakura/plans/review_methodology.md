# 审查方法论与流程教训

## 全量审查方法论

### 两轮审查法（PR53/PR56 经验）
全量审查不能仅"把范围扩大"，需结构化执行：

- **第一轮：规则驱动** — 按 checklist 逐条在全量代码中搜索匹配（volatile 缺失、空 catch、硬编码等模式匹配）
- **第二轮：文件驱动** — 对每个新增/大改文件做独立深度审查

### 链路驱动组织（PR56 经验）
全量审查应按**功能链路**组织，而非按文件列表扫读：
```
配置 → 触发 → 传输 → 处理 → 展示 → 清理
```
按链路组织自然迫使审查者走完完整路径，避免服务端/客户端侧遗漏。

> ⚠️ 增量审查有"广度陷阱"：精力分散到多文件后，反而漏掉对单个新增文件的规则化检查。

## 增量审查标准动作

### diff + 上下文 双模式（PR56_incr2）
- **看 diff 验逻辑**：验证增量修改的正确性
- **扫上下文防遗漏**：从单行修改延伸至全文件同类结构扫描

### 强制边界声明
- `quick` 模式必须在报告中声明审查边界
- 提示扫描同模块历史问题
- 避免开发者误以为整体代码已健康

## 审查偏见与陷阱

### 新代码偏见（PR56 教训）
> 对写得不错的新代码放松审查力度是最常见的陷阱。
> `ClientAuthLockoutManager` 的 synchronized 用得对，但这不意味着其他方面（断线清理、时间窗口设计）没有问题。
> **正面评价 ≠ 审查意见**，>50 行文件仍需至少 1 条改进建议。

### 安全审查需攻击者视角（PR56 教训）
> 安全控制能否被绕过？不能仅通过"读代码发现 Javadoc 与实现不一致"来发现安全 bug，
> 必须从攻击者视角验证：构造输入能否绕过限流/锁定/认证？

### 全量审查 ≠ 逐文件扫读（PR53/PR56）
- 横向一致性优势：跨文件对比发现 volatile 不一致
- 纵向深度不自动改善：需链路驱动补充深度

## 审查模板建议

### 必选项
1. [ ] 新增文件列表（>50 行需有意见）
2. [ ] 是否波及同模块历史问题
3. [ ] 安全机制审查（有则 attacker 视角验证）
4. [ ] 配置变更逐项审查
5. [ ] Mixin 兼容性评估（有 Mixin 则必填）
